## 三、逐层执行方案

### 层 0 · 会面卫生（v10.12.1）—— 只做客户在屏幕上看得见、且改动是纯数据的

**做什么**

1. **开票主体包化**（设置 #6）：两个包已有 `IDENTITY`，播种器 `:687-690` 与 `:756-765` 改读包；ABN 换成**校验位不通过**的号（照 `:858` 的 `61 111 222 333`）。
2. **Xero 组织名包化**（设置 #8）：`:1023` 改由包的 `NAME` 派生，加进 `_select_pack` 的 required 元组。
3. **年龄 / 生日 / 充值 / 薪酬脱离 index 算术**（设置 #20 + 排课 #18）：STUDENTS 元组加 `age_years`、`birthday_md`（固定月-日）；`CREDIT_PURCHASE`、`TEACHER_PAY` 各成一个包结构。**这一条同时修掉**：10 岁坐在 4–6 岁班、12 人生日扎堆一周、$585 × 12 的累计收款、Hannah 90 分钟课与 SCHEDULES 里 60 分钟的矛盾。
4. **四处「画艺大进」**（排课 #14）：`dashboard.jsx:213/220/230/237` 改 `renderMessage('birthday', …)`。`birthday` 是服务端白名单内的模板键（`_shared.py:1218`），有默认值，**不需要新增任何管道**。
5. **完整重播种两个包**（设置 #7 的原因：错的主体已冻进 4 张已开具发票的快照，改设置救不回来）。
6. `test_showcase_tenant.py` 加两条断言：学员年龄落在所排课程的 `age_range` 内；任意 14 天窗口内生日人数 ≤ 名册的 10%。

**不做什么**：不动设置页 JSX、不动排课页结构。会面前动 4148 行文件里的渲染体是不划算的风险。

**代价**：播种器 + 两个包 + `dashboard.jsx` 四行 + 测试。需要 `build_cms.sh` 重建 + 部署 + 两次重播种。美术包的生日分布会跟着变——这是**同一个 bug 的同一次修复**，不是回归；今早锁住的计数断言（12 学员 / 15 作品 …）不受影响。

**零成本兜底**（没有验证窗口时）：会面时**不打开「系统设置」，不展开「近 14 天生日」，发票只开美术租户的**（对美术租户而言 Paradise Production 是「正确」的示例主体）。音乐租户的名单页里 Chloe 10 岁这条躲不掉，但不点进学习报告就不会对上文案。

### 层 2 · 两页同批重构（v10.13.0）

**顺序：路由 → 设置页 B → 排课页甲 → i18n → 测试契约。** 路由先改是因为两页都依赖它。

**① 路由（一次改动）**

`readCmsRoute` 把 `section` 按 `tab` 作用域解析：

- `tab=settings` → 对照 `SETTINGS_SECTIONS` 白名单，不中回落 `account`；再按角色收敛并 `replaceState`（设置 #3）
- `tab=roster` → 对照 `['checkin','plan']`，不中回落 `checkin`
- 其他 tab → 忽略 `section`

状态仍是两对（`settingsSection` / 新增 `rosterSection`，照 `setPendingTab` 的形状），只是**解析器只有一个、白名单在一处**。排课文档担心的「污染 `settingsSection`」在作用域解析下不成立。

> 这是整合者的合成，两份源文档都没有。若实现时发现 `popstate` 还原等细节变复杂，退回排课文档的「独立参数 + 第三对 state」方案，不要硬凑。

**② 设置页：方案 B，但 tab 原语换成 `Tabs`/`TabPanel`**

方案 B 的内容照做（三组：我的账号 / 工作室 / 连接与数据；删 `workspace`；Xero 队列搬进 `billing.jsx`；`?section=` 7→3 重定向表；侧栏入口按角色选默认分区）。

**唯一的整合改动**：不保留手写 strip，改用 `components.jsx:228` 的 `Tabs` + `:268` 的 `TabPanel`。方案 A/B 原文是「面板挂载改条件渲染并共用 `sectionVisible(key)`」——`TabPanel` 的 `if (!active) return null` 就是那个条件渲染，只是有了名字。两页用一个原语，意味着：

- 设置页那次翻车的失败模式（默认可见、加一行才归属）在**两页**上都结构性消失
- 两页的测试能用同一句话验收：**拿掉分段控件，页面只剩共享块**
- 不可达的弹窗分支（设置 #22）顺手删掉，七处 `hidden` 消失

**③ 排课页：方案甲**

1. 删生日横幅 `scheduling.jsx:92-113`，工作台的两行合并成一行 7 天窗口、改用 `cms-app.jsx:953-968` 的跨年正确算法、套 `names(arr,4)` 截断（排课 Q1、#12、#13、#16）
2. 顺序改成 `共享 → 签到 → 排课`
3. 概览条**搬出** `.cms-roster-planner` 卡再 `sticky`（文档已指出卡内 sticky 只能吸到 752px）
4. 时段安排默认折叠
5. 一对一面板 `onToggle` 懒加载（照 `components.jsx:786-787` 的学员时间线）—— 4 个请求离开签到路径
6. 顺手：排课 #4–#11（日报「今日」写死、转为每周班次不展开、保存模板漏课表学员、手机菜单不关、≤360px 周视图重叠、空态方向词）

**④ i18n 一次扫**：设置 #9/#10/#11/#27 + 排课「今日签到」「排课设置」，末尾跑 `audit_cms_translation.py`。

**⑤ 测试契约同 PR 重写**：`test_cms_navigation_names.py` 从源码解出分区 key 逐个断言；`ROSTER_UI_CONTRACT` 按「共享块 + 当前段」分别断言并保留 `noOverflow`；两处都加「每个角色下 `count(tabpanel) == count(tab)`」。

**代价**：这是四层里最大的一个发布，但拆开反而更贵——两页共享 `cms-app.jsx` 与路由层，分两个发布等于把同一段代码改两遍。

### 层 3 · 排课页分段（v10.14.0）—— 由一个产品判断决定形态

层 2 的甲上线后看两周。**如果仍然满**（第一行学员仍在首屏之外），上乙：`Tabs` 两项「今日签到 / 排课设置」，日期 + 周视图 + 概览条留在控件之上。路由、原语、测试形状在层 2 都已就位，乙本身只剩搬块。

## 四、整合者加的三处（两份源文档都没有，单独标出）

1. **路由按 tab 作用域解析 `section`**（层 2 ①）。好处是白名单只写一处、两页共用；坏处是比排课文档的「再加一个参数」多一点解析逻辑。若实现别扭就退回。
2. **设置页也用 `Tabs`/`TabPanel`**（层 2 ②）。源文档 A/B 都保留了手写 strip，只把面板改条件渲染。换原语多花的工是换标签；换来的是两页一个失败模式防线、一句话验收。
3. **层 0 的取舍由会面决定，而不是由严重度决定。** 按严重度，越权（设置 #1）该排第一；但它对会面不可见（Lee 用 owner 演示），而演示数据的矛盾对会面可见。所以层 0 是「可见 + 纯数据」，层 1 才是「严重」。会面一过，这个排序就失效，层 1 立即上。

## 六、整合后的风险

- **`cms-app.jsx` 同一文件两条改动流**：已用串行（设置 → 排课）规避；不要开两条分支并行改它。
- **每次 JSX 改动都要 `build_cms.sh` 重建**：`cms-app.js` 是 esbuild 产物，手改无效且会被覆盖。
- **层 0 是会面前的生产部署**：改动面是播种器 + 四行文案，但仍是部署。层 0 的「做 / 不做」就是「有没有验证窗口」，不是「有没有时间改代码」。
- **层 2 重定向表（设置 7→3）上线当天，旧书签的行为会变**：必须与 `?section=` 白名单同批，否则修好泄漏当天老链接变空页（设置文档已强调）。
- **两份源文档各有标注为不确定的条目**（设置：七 tab 切分是否真错、往返次数无埋点；排课：①②频次对比、只留②仍差一行、移动端 1088px 后的外推）。这些不确定性**全部落在层 3 和方案 C 的选型上**，不影响层 0–2。层 0–2 的每一条都有 file:line 或实测。
