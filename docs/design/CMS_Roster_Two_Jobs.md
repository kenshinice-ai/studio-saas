## 主 agent 实测：三条已在本地端到端复现

正文的关键结论我挑了三条自己复现，因为它们要么牵涉钱、要么客户当场看得见。

### 一、未来日期签到会真的扣课时（正文第 1 条，实测确认）

服务端规则在 `api_v1/students.py:1430`：`class_date > today + 1 天` 才拒绝。
也就是**「明天」是放行的**。本地对音乐样板租户实测（manager 身份）：

| 选中日期 | HTTP | 结果 |
|---|---|---|
| **明天（+1 天）** | **201** | **Isabella 余额 12.0 → 11.0，为一节还没上的课扣掉一个课时** |
| +2 天 | 400 | `classDate must be within the past 90 days (or tomorrow at most).` |
| +3 天 | 400 | 同上 |

边界与代码规则精确吻合。危险的不是报错那一侧，是**静默成功**那一侧：
界面在任何选中日期都照常渲染蓝色主按钮「签到并扣 1 课时」，
选下周三得到一句英文原文报错，选明天则什么都不说，直接扣。
批量确认框（`cms-app.jsx:1913`）连日期字都不提。

（实测在本地库进行，测试后已重新播种复原；生产未触碰。）

### 二、front_desk 根本进不了这一页（正文引用，实测确认）

`cms-app.jsx:296-304` 的 `roleTabs`：

```
front_desk: ['dashboard','pending','students','new_student','billing','topup','logs','settings']
```

**不含 `roster`**，而 `:402-404` 的 effect 会把访问未授权 tab 的人踢回 dashboard。

这条改变了受众判断：日常签到实际由 owner / manager / teacher / staff 做，
不是前台。我在上一轮回复里说过「前台常用平板签到」，那是错的，以这条为准。
它同时是「生日横幅该归工作台」的最硬证据——横幅所在的页面，
它最该服务的角色根本打不开。

### 三、工作台的生日祝福写死「画艺大进」，且直接预填短信（正文 Q1，实测确认）

`dashboard.jsx` 共**四处**写死「愿新的一年里画艺大进，心想事成」：
`:213`、`:220`、`:230`、`:237`。其中 `:220` 与 `:237` 不是复制到剪贴板，
而是 `sms:` 链接的 `body` 参数——点一下就是一条预填好、发给家长的短信。

在知音音乐（钢琴 / 小提琴 / 古筝）租户上，这是要发给琴童家长的原文。

同一个仓库 `cms-app.jsx:409-411` 的注释正好在说这类 bug 修过一次：
「staff 粘进微信的文案以前会写死 Studio 一词并以调色板 emoji 结尾——
对钢琴、舞蹈、游戏租户是错的，而且家长直接看得到。」
这四处是当时的漏网。修法与那次一致：走 `renderMessage` 模板，不写字面量。

## 一、两个答案

### Q1：生日提醒该放哪？

**不搬 —— 删掉，然后把它的优点并进工作台已有的那一份。**

工作台"今日待办"里**早就有两行生日**：`dashboard.jsx:209-225`（本周生日）、`dashboard.jsx:226-242`（本月生日）。课程安排页那块（`scheduling.jsx:92-113`）是**第二份实现**，不是唯一一份。所以本轮的问题从来不是"移到哪"，而是"删哪一份、把哪一半的优点合并过去"。如果照"搬到工作台"直接执行，工作台会出现三行生日。

而且要删的那一份恰恰是算得对的那一份：

- `cms-app.jsx:960` 用 `new Date(y, m, d+i)` 逐日推进，**跨年自动进位**；`dashboard.jsx:156` 用 `new Date(now.getFullYear(), 月, 日)` 构造当年日期，12 月最后一周会漏掉全部 1 月生日。
- `scheduling.jsx:94` 走 `renderMessage('birthday', …)`，尊重租户文案模板；`dashboard.jsx:213/220/230/237` 四处把"**画艺大进**"硬编码了 —— 钢琴、舞蹈、游戏租户的家长会收到画室文案。`cms-app.jsx:408-411` 的注释写明这个坑修过一次，dashboard 这四处是当时的漏网。
- `scheduling.jsx:100-109` 是"一人一个按钮，点一次得一个人的文案"；`dashboard.jsx:213/230` 是把所有人的祝福 `join('\n')` 拼成一坨，250 人租户本月约 20 条粘在一起，实际不可用。且生日行是今日待办里唯一**不截断**的一行（其他三行都用 `dashboard.jsx:161` 的 `names(arr,4)`）。

归属选工作台的最硬证据是角色：**front_desk 根本进不了课程安排页** —— `cms-app.jsx:402-404` 的 effect 会把它踢回 dashboard。而"今日待办"整块无角色判断（`dashboard.jsx:150`），owner / manager / teacher / front_desk 全都看得到。也就是说生日横幅从一开始就投给了错的受众；搬到工作台不是妥协，是纠正。

**具体动作**：删 `scheduling.jsx:92-113` 与 `scheduling.jsx:68` 的解构、`cms-app.jsx:3653` 的 prop；保留 `cms-app.jsx:953-968` 的计算并改由 `dashboard.jsx` 消费，替换掉 `dashboard.jsx:156-157` 的两套自算；删掉"本月生日"整块（`dashboard.jsx:226-242`，注意收尾行是 242，切在 241 会留下语法错误），统一成 7 天滚动窗口（与 `backend/server.py:775-787` 周报邮件的 7 天窗口一致）。

**注意**：这件事**买不回首屏空间**。生日块是条件渲染（`scheduling.jsx:93` 的 `length>0` 门），默认折叠只有一行 summary，删掉只买回约 4.5px。真实租户 12 人名册在任意 14 天窗口里通常一个生日都没有 —— 也就是说线上大多数时候这页**本来就是"没有生日块"的样子**，而那个样子第一行学员仍在 897px、仍然看不见。演示租户显示"12 人"是播种 bug（见第四节）。所以生日该删，但不要把它当作首屏方案，否则改完看起来会像什么都没变。

### Q2：有没有必要引入 tab？

**必要，但是"页内 tab"，不是新增导航项；而且 tab 是必要条件不是充分条件，单靠它这页还是挤。**

必要的量化理由：**两个职能的成本是不对等的**。只做②的人每次进页面要跳过①和③的 **425px**（桌面可用窗口 836px 的 51%，移动端可用窗口 738px 的 58%）；只做①的人只需跳过②的 150px。桌面 1440×900 下第一行学员在 **958px** —— 打开这一页，**一个学员名字都看不到**。真机笔记本减掉浏览器 chrome 只剩约 800px 视口，比这更糟。这不是"页面有点点满"，是①在向②按天收租，而折叠已经用到头了（四个顶层 `<details>` 全部默认关闭，页面还是这样）。

同时有三条限定：

1. **不要新增导航项。** 手机底栏只有四个位置（`cms-app.jsx:4126`），两个之中必有一个掉进"更多"抽屉，恰好把 Lee 说的两个重点之一降级。
2. **不要抄设置页那条手写 strip。** 设置页翻车的原因不是 tab，是 **hidden 式"选择性认领"**：默认可见、加一行 `hidden=` 才归属，漏了就静默重复渲染（那里实际约六块裸奔，不止四块）。改用 `components.jsx:228` 的 `Tabs` + `components.jsx:268` 的 `TabPanel`（`if (!active) return null`），未认领的块会**整块消失**，第一眼就看得见 —— 这个失败模式在结构上不可能重演。
3. **只加 tab 不够。** 就算把①整个搬走，②自身的家具（日期导航 88 + 周视图 68 + 概览条 41 + 时段安排 85 = 282px）仍吃掉可用窗口的 34%，第一行学员在约 524px，6 行到约 956px，仍然超出 900 视口。（这一段是按实测块高做的推演，未在浏览器里复现，标为**估算**。）所以②那一栏必须同时做概览条吸顶 + 时段安排默认折叠。

## 二、这页到底哪里满

### 满的机制：不是"东西多"，是"两个职能交错排列"

顶层区块的实际顺序（括号内是归属）：

```
1v1循环课①  生日③  固定课表①  日期+周视图①②共用  概览条②
时段安排①   添加学员①  班组模板①  当日四按钮②  当日名单②
```

即 `① ③ ① 共用 ② ① ① ① ② ②`。②被①从两侧夹住，中间还插了一段。**这才是"满"的来源** —— 同样这些区块，若按职能聚成两段，②的路径上一块①都不用跨。

分项实测（桌面 1440×900，`capture_manual_shots.py:53` 的 DESKTOP 视口，deviceScaleFactor=2）：

| 挡在②前面的 | 高度 |
|---|---|
| 1v1 循环课（折叠条） | ~72px |
| 生日（折叠条，多数租户不渲染） | ~4.5px |
| 固定课表（折叠条） | ~52px |
| 日期 + 迷你周视图（共用） | ~154px |
| 时段安排 | 94.9px |
| 添加学员 + 班组模板 | ~150px |
| **合计** | **≈425px** |

移动端 390×844：底部 tab 栏上沿在 794，可用窗口 738px；第一行学员外推在 **1173px**，要滚 383px 才看到上沿，6 人名单看完要滚约 1167px ≈ 1.6 屏。（1088 之后的数字是外推 —— 截图在 844px 处被裁掉，未渲染证据。触发这些版式变化的是容器查询 `@container roster-planner (max-width:680px)`（`index.html:891`），不是视口 media query，验收要按容器宽度而非屏幕宽度做。）

横向对比同库：操作日志、账单发票都是"筛选条 → 立即接列表"。**课程安排是唯一一个打开后看不到任何一条数据的页** —— 这不是全站基线，是这一页的异常。

### 确认的缺陷（与分区方案无关，独立成立）

**钱的路径上，三条：**

1. **一个 rDate 服务两种日期语义，而两边的合法区间不同。** 排课无上限，签到被 `students.py:1430` 限制在 `[today-90, today+1]`。把日期拨到下周三排课，名单每行仍渲染蓝色主按钮"签到并扣 1 课时"，点下去返回英文原文 `classDate must be within the past 90 days (or tomorrow at most)`；而拨到**明天**它会成功 —— 为一节还没上的课真扣掉课时。批量确认框（`cms-app.jsx:1913`）连日期字都没有。
2. **签到状态只从最近 500 条流水推导，会二次扣课时。** `tenant.py:857` 的 `LIMIT 500` 不按 `transaction_type` 过滤（充值/退费/调整全算进去）。危险窗口是"日期在 today-90 之后（服务端放行）"且"已掉出 500 条窗口（前端以为没签）"的交集：一个月流水超过约 167 条的租户（≈40 名学员每周两课），500 条只覆盖 40 余天，41–90 天前的任何一天都会显示"待上课 / 已签到 0"，批量签到即重复扣。演示租户 500 条覆盖约 10 个月，被 90 天下限完全挡住，测不出来。
3. **批量签到失败不给原因。** `cms-app.jsx:1924-1928` 把每个失败塞进数组，最终只显示"成功 N 人，失败 N 人（姓名）"。操作者拿不到"为什么"。

**文案与动线，五条：**

4. `cms-app.jsx:1912-1913` 的确认与提示写死"今日"，`copyRosterDaily` 的日报同样写死"今日上课 N 人"，但它们读的是任意选中日期 —— 排下周三的课时点"日报"，复制进家长群的第一句就是"今日上课 12 人 · 下周三的日期"。批量提醒（`cms-app.jsx:1898`）带了日期但用未来时态，选过去日期同样错乱；`scheduling.jsx:583` 是同一句话的第二份拷贝。
5. **"转为每周班次"点了像坏了。** `scheduling.jsx:474` → `cms-app.jsx:1725-1732` 只做 `setSchedEdit` + toast，而编辑器渲染在 `scheduling.jsx:183`，其容器 `<details>`（`scheduling.jsx:116`）没有 `open`，全仓无任何代码打开它。这是①内部唯一一条跨区块动线。
6. **"保存当前为模板"看不见固定课表来源的学员。** `cms-app.jsx:1953-1954` 读 `db.rosters[rDate]`（只含手动排课），界面显示的人数却是 `cms-app.jsx:1096-1099` 的 `dayIds`（课表 ∪ 手动）。表头写着 12 人，点按钮弹"当前日期没有排课可保存"。
7. **手机"当日操作"菜单点完不关。** `scheduling.jsx:486-489` 四个按钮都没有关闭逻辑，对照同文件 `scheduling.jsx:579/580/584/585/587` 每个菜单项都写了 `e.currentTarget.closest('details')?.removeAttribute('open')`。点完"批量签到并扣课时"后，270px 宽的菜单继续压住紧接着要核对的名单前几行 —— 恰恰这一步之后最需要立刻看到"已签到"变了。
8. **空状态方向词是反的。** `scheduling.jsx:513` 写"也可以直接在下方添加学员"，而 `#rosterAddStudent`（`scheduling.jsx:431`）在 DOM 里位于名单卡片（`scheduling.jsx:480`）**之上**，CSS 里也没有任何 `order:` 重排。

**移动端，一条：**

9. **迷你周视图在 ≤360px 上七个按钮互相重叠**，相邻两天点击区重叠 1–6.7px，重叠区归后一个兄弟节点 —— **选周三会选中周四**，然后整屏名单都是错的。触及 320–360px 的机器（iPhone SE 1 代/5、大量安卓）。流水线唯一在跑的 390px 恰好是最后一个还没重叠的宽度（第七个按钮已越出卡片 1.71px），所以测不出来。

### 设计弱点（不是缺陷，但决定这轮怎么改）

- **全页零 sticky。** 概览条"已签到 3 / 待上课 3 / 低余额 1"是签到过程中唯一的进度反馈，而它在你开始签到的那一刻滚出屏幕；同时日期也看不见了。扣课时的按钮（`scheduling.jsx:505`）按下时，"哪一天、几个人"都不在屏幕上。
- **`<details>` 只藏像素，不省挂载、不省请求。** 一对一循环课面板即使从没被展开，每次进这一页都发 **4 个并发请求**（`private_lessons.jsx:53-56`，`useEffect` 在 `:73`）。签到是站着做的事，这 4 个请求全在关键路径上。这条同时是"再加一层折叠不会让这页变轻"的直接证据。
- **`<details>` 是这一页唯一的密度工具**，全仓独此一家（`scheduling.jsx` 6 处，整个 `legacy-root/src` 才 14 处）。库里被验证过、且已有可复用组件的密度手法只有 `Tabs`。
- **展开即崩。** ①的四块用 details 顺序堆叠，展开任一块都把名单进一步推出首屏。这页现在的"刚好装得下"只在**没人使用它**的前提下成立。（这一条从普通流布局即可确证；具体像素未实测。）
- **`summary` 不在项目的 focus-visible 合约里**（`ui-tokens.css:59`），而这一页几乎全靠 summary 开合。

## 三、思路：这条线该切在哪

### 1）共享的只有一样：日期上下文

日期选择器 + 迷你周视图（`scheduling.jsx:329-342` 的 label 与 date-nav，加 `:344-368` 的周视图）**必须落在分段控件之上、两个段落之外**。

理由不是"两份会不同步" —— 那是错的：`scheduling.jsx:338` 是受控 input，绑定 App 里唯一的 `rDate`（`cms-app.jsx:184`），放两份也永远同值。真实理由有两条：

- **划给①，②就没有日期控件。** 而"今日签到"实际按 rDate 扣课时，`batchCheckIn` 的文案又一个日期字都不提 —— 操作者会把 12 个人的课时按下周三扣掉。扣课时不可静默回滚（撤销要走 `cms-app.jsx:1417-1452` 逐人确认）。
- **两边各放一份**，就是设置页那次翻车的形状：同一块要在多个段里出现。

**建议连概览条一起提到 Tabs 之上**（它同时是"今天到底选的是哪天、几个人"的唯一显示），并让这一条 sticky。注意：概览条现在长在 `.cms-roster-planner` 卡内，sticky 的包含块就是这张卡，只能吸到滚动约 752px 就被推走 —— 要真正贯穿整张名单，**必须先把它搬出 planner 卡**。"零结构改动就能吸顶"这句话不成立。

### 2）真正干净的切线不是标题上的①/②，是"周期结构 vs 某一天"

按标题切会出错，因为有两个动作名字属①、数据属②：

- **添加学员**（`scheduling.jsx:431-452`）→ `addToRoster`（`cms-app.jsx:2802-2834`）写的是 `rDate` 这一天的 `daily_roster_entries`。
- **班组模板的"套用到当前日期"**（`scheduling.jsx:467`）→ `applyGroup`（`cms-app.jsx:1965-1977`）同样写这一天。

这两个动作留在①，①就被迫也要带日期控件。反过来，把它们归到②之后，①对 `rDate` 的读依赖**只剩 `scheduling.jsx:144` 一个高亮**；去掉那个高亮，①一个日期状态都不需要（固定课表里所有日期默认值都取今天而非 rDate：`cms-app.jsx:1591-1596`、`scheduling.jsx:134`、`cms-app.jsx:1728`）。

所以两段的内容是：

| 段 | 内容 |
|---|---|
| **排课设置**（周期结构） | 固定课表 + 停课/恢复、一对一循环课、班组模板的「保存为模板 / 删除 / 转为每周班次」 |
| **今日签到**（某一天） | 时段安排、添加学员、「套用模板到当前日期」、当日四按钮、当日名单 |
| **共享（在 Tabs 之上）** | 日期选择器 + 迷你周视图 + 当日概览条 |

几个边界项的判定依据（按"写什么数据 / 需要什么权限"，不按标题）：

- **时段安排**（`scheduling.jsx:389-429`）：全段零 `onClick`，是纯读的冲突校验；代码注释（`:386-388`）说它要解决的是"一对一被订进已占用的小时"—— 这是订课错误。语义偏①，但它是当天的冲突，**放②里默认折叠**最省事。
- **导出当日 ICS / 批量提醒**：价值在**非今天**的日期上最高（提醒文案是未来时态），却被排在②的按钮群里。这轮不动，但知道它们不是纯②。
- **权限不重合，所以不能用权限来切。** 这页横跨四个域：固定课表要 `tenant_admin`、1v1 要 `scheduling:write`、添加学员/套用模板/签到都是 `attendance:write`（同一把钥匙、两张不同的表 —— 签到写 `credit_transactions`+`attendance_sessions`，添加学员写 `daily_roster_entries`）、模板保存走 legacy `save()` 要 `students:write`。上面这条切法**比①|②少劈开一个域**，但没有任何切法能让某一侧成为单一权限域。

### 3）状态不是障碍，别拿它当否决理由

`RosterSection` **一个 hook 都没有**（`grep useState|useEffect|useMemo|useRef` 零匹配），rDate / schedEdit / schedules / dayIds / rosterDone 全住在 `App()`。分段切换不会丢值，也不会重新请求。

真正会丢的只有三类非受控状态，且它们决定用哪种分段写法：

| 会丢的 | 位置 | 后果 |
|---|---|---|
| 4 个顶层 `<details>` 展开态 | `scheduling.jsx:77/94/116/456` | 切回来固定课表又收起来了 —— 烦人，不是缺陷 |
| `StudentPicker` 的搜索词 | `components.jsx:542-548` | 轻微 |
| **1v1 建课表单草稿** | `private_lessons.jsx:424` 的 `useState({...})` | 真会被抹掉 |

**取舍**：条件渲染（`TabPanel`）会丢这三样，但**自动消掉那 4 个请求**；`hidden` 保住状态，但请求照发。建议**用 `TabPanel` 条件渲染 + 把 1v1 的 `load()` 改成 `onToggle` 首次展开才拉** —— 库里有现成先例，`components.jsx:786-787` 的学员时间线写的正是这个形状。两头都拿到。

（顺带划掉一个流传的说法：`RosterSection` 里是 **6 处** `<details>`，不是 28；整个 `legacy-root/src` 一共才 14 处。其中两处是瞬时菜单，丢了正好。不要用 details 数量当反对分段的论据。）

### 4）验收只问一个问题

**删掉分段控件之后，页面还剩哪些块？答案必须是"只剩共享块"。** 这一句话就能拦住设置页那个失败模式。

## 六、不建议做的事

1. **不要把生日"搬"到工作台。** 那里已经有两行，搬过去会变成三行。是删 + 合并，不是搬家。
2. **不要把生日放进"待处理"tab。** 语义是"外部申请等我批准"，生日是"内部提醒等我行动"；`students.jsx:284-287` 的注释正是为了防这种混算。而且 teacher 看不到 pending。
3. **不要把生日放进学员档案。** 要新增一个 filter（`cms-app.jsx:973-993`）加一条排序，比复用已有的待办行贵；档案的语义是"查某一个人"，不是"今天该做什么"。
4. **本轮不要把生日接进通知发送体系。** 技术可行，但要给它 event key、默认路由、配额和退订语义（家长退订账单短信是否连生日一起退？），是一次会产生真实短信费用、且带营销性质的自动外发 —— 商业决策，不该混进一次布局整理。先例摆着：`DEFAULT_ROUTES` 里 `lesson_reminder` 是故意留空的。
5. **不要抄设置页那条手写 hidden strip。** 用 `Tabs` + `TabPanel`。
6. **不要"再加一层折叠"。** 四个顶层 details 已经全部默认关闭，这条杠杆用完了；而且 details 只藏像素，不省挂载、不省请求。
7. **不要拿演示租户"12 人生日"当拥挤证据。** 那是播种 bug。生日块的真实成本是一行折叠标题，多数日子根本不渲染。
8. **不要用"28 处 details 会丢状态"当反对分段的理由。** 实际 6 处，其中 2 处是瞬时菜单。
9. **不要做推挤式抽屉。** 1280px 视口下主列约 1040px（桌面侧栏固定 240px），开一个 320–400px 推挤抽屉主列只剩 590–670px，**同时跌破 760px 和 680px 两个容器断点** —— 点名行整排改版式、添加学员塌成单列。要做只能做覆盖式，但那就退化成模态，和"排课模式"的意图不符。
10. **不要只做"搬走生日"就收工。** 首屏一个学员都不会多出来。
