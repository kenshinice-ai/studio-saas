## 结论

1. **两份材料的大方向一致：不接 Cal.com 的服务，不搬它的代码，只借机制。**
2. **顺序上采纳云端建议书，撤回本机初读的「先做试听自选时间」。** 初读说「老师可约时段的数据基础已经有了」，这句不对：表在，但没有任何代码读或写它（见第二节）。
3. **在云端建议书之上改三处：**
   - 日历订阅源不只是代码缺陷。客户版本记录从 v10.0.0 起就写着「家长可以订阅」，而后台没有发放入口。这是「说了但用不了」。
   - 提醒拆成两段。事件触发的邮件（申请已批准、课程取消）不需要调度器，可以先做。只有「课前 24 小时」需要调度器。
   - 自助请假先放进学员专区，不先做凭链接的入口。学员专区已经有登录，不需要新的凭证。
4. **限时占位是真取舍，不是显然该做。** 现有设计刻意不占位，理由写在设计文档里。见第三节步骤 2。

## 三 · 汇总后的方案

每一步写四件事：做什么、为什么、争论点、倾向。

### 步骤 1 · 让日历订阅源真的能用

**做什么**
- 修 token 查找，使它在受限角色下能找到行。找到后绑定租户，再读课程。
- 把周几统一成周日 = 0。
- 把补课加进订阅。
- 在后台加发放入口：给一个家庭或一位老师生成链接，可吊销。
- 加一条在受限角色下真正请求该地址的测试。

**为什么先做**
- 客户文档已经承诺了它。
- 它是最便宜的提醒：不花钱，不需要调度器。
- 步骤 3、4 里凡是「凭 token 的公开查找」都会撞同一堵墙。这里先定解法。

**争论点：token 查找怎么过 RLS**

| 做法 | 先例 | 代价 |
|---|---|---|
| A · 一个只返回租户 ID 的查找函数（`SECURITY DEFINER`），表本身仍强制 RLS | 没有先例 | 多一种机制；授权脚本要认识它 |
| B · 把表加进豁免清单 `EXEMPT` | `share_tokens`、`password_setup_tokens` | 这张表从此只靠应用层过滤 |
| C · 给表加一条 `USING (true)` 策略 | `xero_oauth_states`（`0045`） | 效果同 B，名义上还在 RLS 里 |

**倾向：A。** 暴露面最小：未绑定的连接只能用完整 token 换到一个租户 ID，读不到别的。B 有先例、最省事，可以作为退路。这是改租户隔离的做法，按 `AGENTS.md` §24 要 Lee 先点头。

**顺带一个教训。** 这是同一类问题第二次出现（上一次是 Xero 回调）。两次都是：测试用属主角色跑，或者根本没有请求那条路由。建议加一条总测试：列出所有凭 token 的公开路由，逐条在受限角色下请求一次。

**在修好之前**，版本记录和 `Integration_Boundaries.md` 的那两段与事实不符。如果步骤 1 排不进下一次发布，就先改这两段文字。

### 步骤 2 · 限时占位

**做什么（云端建议书的版本）**
- `class_bookings` 加 `hold_expires_at`。待确认的申请占一个座位，到期自动释放。
- 剩余名额 = 容量 − 已报名 − 已批准 − 未过期的待确认。
- 并发靠锁住班次那一行，在同一事务里数座位。
- 过期不需要定时任务：读取时按到期时间过滤。

**为什么**
- 家长提交后不知道位置是不是自己的，犹豫期里可能被别人约走。
- 竞品对比文档把它列进「如果只做三件」（`Competitor_MyMusicStaff.md:61、100`）。

**争论点**
- 现有设计是**刻意**不占位，理由一句话：「一个随手点的请求会挡住一个真要来的人」（`Public_Timetable_And_Booking.md` §3.1）。它用「告诉家长排第几个」来补（§3.2）。
- 这个入口不需要账号。占位之后，任何人连续提交几次就能把一个班显示成满员。现在只有按 IP 的限流。
- 占位多久合适，取决于租户实际多快回复。这个数字我们没有。

**倾向：做，但带三个条件。**
1. 同一个电话在同一个租户里同时只能有一个占位。
2. 时长是租户设置。默认值先用 48 小时（出自对比文档的建议，不是测出来的）。
3. 和工作台的「未回复的预约申请」一行同时上：那一行显示「还有多久过期」。否则占位只是把问题从家长挪给了没人看的列表。

如果 Lee 更看重简单，**不做也站得住**：只上工作台那一行，让申请被更快处理。

云端建议书顺带提的黑名单和「被拦截的人仍看到已提交」，等真有滥用再做。

### 步骤 3 · 给家长的通知

拆成两段。

**3a · 事件触发的邮件（不需要调度器）**
- 预约申请被批准、被拒绝。
- 课程被取消、被改期。
- 做法：让 `dispatch()` 第一次有调用方，接上已有的路由表、发送日志、退订表（迁移 `0038`）。

**3b · 定时提醒（需要调度器）**
- 课前 24 小时提醒。
- 需要「某个时间点做一件事，可取消，可重试」。云端建议书建议把 Xero 的作业表泛化成一张通用任务表，加一个 systemd 定时器。

**争论点**
- 自动给家长发邮件是租户对外的行为。发错、发重、发到退订的人，租户的客户都看得见。
- 默认路由里「课程取消 → 短信」，而短信适配器一律报错。也就是说，就算接上了，取消通知默认也发不出去。3a 要把取消和改期的默认渠道改成邮件，或者明确留空。
- 「试点期不引入调度器」（`Architecture.md:338`）。那一行和 Redis、消息队列并列，说的是新的基础设施部件。一张表加一个定时器是已有做法的延伸（Xero 推送、备份）。字面上仍然冲突，要 Lee 定。
- 时间一律按租户时区算。

**倾向**
- 3a 做。每个租户默认**关**，由租户自己打开。先只做「申请被批准 / 被拒绝」两封，因为它正好接在步骤 2 后面。
- 3b 等步骤 1 上线后再看。订阅源能用了，定时提醒的大部分需求就没有了——这正是当初把 `lesson_reminder` 默认留空的理由。
- 任务表不提前建。等到 3b 确定要做，再和它的第一个使用者一起建。

未核实：生产上的发信通道是否已经配置；批准之后家长现在是否真的收不到任何消息（云端建议书的说法）。

### 步骤 4 · 家长自助请假

**做什么**
- 家长看到自己孩子接下来的课，对某一次点「请假」。
- 系统按租户已设的规则处理：提前量够就发补课额度，不够就按规则计费。规则已经写好（`resolve_absence()`、`scheduling_policies.notice_hours`），只缺入口。
- 提交前把后果说清楚：「现在请假会得到一次补课额度」或「已过截止时间，这节课仍会计费」。
- 过了截止时间不给按钮，只显示联系方式。

**争论点：入口放哪里**

| 入口 | 凭证 | 依赖 |
|---|---|---|
| 学员专区 | 已有：姓名 + 电话 + 六位访问码，一小时会话 | 无 |
| 邮件里的链接（云端建议书） | 新的：每节课一个 token | 步骤 1 的 RLS 解法、步骤 3 的邮件 |

**倾向：先学员专区。** 不需要新凭证，不依赖邮件。链接入口等 3a 的邮件稳定后再加，届时只是多一个入口，规则不重写。

**前置条件**：先修提前量的时钟（第二节 #10）。家长自己操作之后，「差一小时算不算提前」就是钱的事。

这一步让家长能改动影响课时和计费的记录，是授权范围的变化。按 `AGENTS.md` §24 要 Lee 先点头。

第二段（家长用补课额度自己约补课）等这一段跑顺再议。

### 步骤 5 · 试听自选时间（时段引擎）

**现状比初读估计的差**：老师可约时段的表没有任何读写，也没有录入界面；报名记录上没有时段字段；没有时段计算。要做的是四件事，不是一件：录入界面、时段计算、试听这种「预约类型」的定义、报名流程里的选择步骤。云端建议书估 2–3 周（它自己标了「推断」）。

路线图 §9 把复杂排课列为现阶段不做。

**倾向：现在不做。** 「没人回复的试听预约」这个痛点，先由工作台的例外行（看得见）和 3a 的邮件（家长收到答复）解决。如果这两样上线后，试听仍然卡在「来回约时间」上，再回到这一步。届时 Cal.com 的时段管线是最值得照着写的部分，云端建议书第二节 6 已经整理好。

### 步骤 6 · 等有租户提出再说

Google / Outlook 双向同步、出站 webhook、嵌入挂件、在线定金。各自的障碍见云端建议书第二节 7，本文不重复。

云端建议书第二节 5 列了五条。现在只取一条：步骤 1 里那条「受限角色下逐条请求公开 token 路由」的测试。其余（规格目录、权限对照表、规则卡）不解决眼前的问题，暂不动。

## 四 · 和工作台「例外清单」的关系

两个方案不冲突，而且互相需要。

| 工作台例外行 | 和本方案的关系 |
|---|---|
| 没人回复的试听预约 / 预约申请 | 步骤 2 让它有了期限；步骤 3a 让家长收到答复 |
| 快到期的补课额度 | 步骤 4 第二段（自助约补课）才能从源头减少它 |
| 连续几周没来的学员 | 步骤 4 之后，请假有了记录，「没来」和「请了假」才分得开 |
| 课时快用完、逾期发票、逾期报告 | 无关 |

**顺序含义：工作台例外清单应当排在步骤 2 之前或与它同时。** 它不依赖本方案的任何一步，而步骤 2 依赖它。

## 五 · 不做的

- 把托管版 Cal.com 接成排课核心：租户数据出了我们的 RLS 边界；没有课时、补课额度、学期的概念。
- 自部署 Cal.diy：它的 README 自己写明不适合生产；栈完全不同。
- 用 Cal.com 做产品站的「预约演示」：要引入第三方，要改安全策略和刚发布的隐私政策。
- 按表单答案分流、轮转分配、总部模板下发：没有对应的场景。
- 拆分前标签里的代码（AGPL 或商业许可）：只读概念，一行不拿。

云端建议书还列了 Cal.com 不如我们的四处（隔离靠应用层、防重只防完全相同的时段、凭证加密没有认证、循环预约只查第一次）。这些我没有读它的源码核实，但结论方向是「保持我们现在的做法」，不需要动作。

## 九 · 自动发邮件怎么实现（2026-10-14）

> 2026-10-14 稍后：Lee 说的「API」是 Claude 的 API，方向改为 Claude 起草、人确认后用自己的邮件或短信发，已在 v10.22.0 上线。本节的 Cloudflare 发信方案没有实施，留给以后「在系统里直接发送」那一阶段。

### 结论

**在应用里加一个 Cloudflare 发信后端，不经过 PWE Assist 的 Worker。** 应用已经有五处发邮件的代码，缺的只是一个真的能发出去的通道。

### 现状（2026-10-14 读代码）

- 发信入口是 `services/notifications.py` 的 `_deliver()`，由环境变量 `STUDIOSAAS_EMAIL_BACKEND` 选：`smtp` 或 `console`。
- 部署模板里的默认值都是 `console`（`deploy/aws/*.example`、`standalone-edition/install.sh:220`）。`console` 只把邮件打印到日志。生产主机上实际是哪个值，未核实（没有登录主机查）。
- 已经在调用的五处，全部用 `send_safely()`（出错不影响主流程）：

| 模板 | 收件人 | 位置 |
|---|---|---|
| `class_booking_admin_alert` | 租户管理员 | `api_v1/public.py:1159` |
| `registration_received` | 家长 | `api_v1/public.py:2282` |
| `registration_admin_alert` | 租户管理员 | `api_v1/public.py:2298` |
| `registration_approved` / `registration_rejected` | 家长 | `api_v1/students.py:724` |

- 模板只有英文。租户可以在 `email_templates` 表里覆盖。
- **缺口**：班课预约申请被批准、被拒绝时，家长收不到邮件。没有对应模板，也没有调用。

### Cloudflare 发信服务（2026-10-14 读官方文档）

- 2026-04-16 进入公开测试。可以用 Workers 绑定、REST 接口或 SMTP（SMTP 2026-06-08 起测试）发送。
- REST 接口：`POST https://api.cloudflare.com/client/v4/accounts/{account_id}/email/sending/send`，Bearer token，权限「Email Sending: Edit」。字段有 `from`、`to`、`subject`、`text`、`html`、`headers`；2026-05-28 起收件人可带显示名。
- 发件域名要先在 Cloudflare 后台接入（会加 SPF、DKIM、DMARC 记录）。接入之前只能发给已验证的地址；接入之后可以发给任何人。
- 新账户有一个保守的每日额度，随发送表现上调。具体数字文档没写。
- 文档写「Workers 付费计划可用」。我们是否已在付费计划上，未核实。

PWE Assist 的 Worker 现在用的是 Email Routing 的绑定，生产配置里收件人固定为 Lee（`PWE-AI-BOTs/wrangler.jsonc:78、119`）。它发不了给家长，也不该替应用发。

### 做法

| 项 | 做法 | 理由 |
|---|---|---|
| 通道 | `_deliver()` 加第三种后端 `cloudflare`，用标准库 `urllib` 调 REST 接口 | 不加依赖；SMTP 还在测试 |
| 发件人 | `"<租户名称> <notify@pwestudio.online>"` | 家长认的是租户的名字 |
| 回复地址 | 租户的联系邮箱（`tenants.contact_email`） | 家长点回复，信到租户，不到 PWE |
| 密钥 | 主机上的环境文件，不进仓库 | 和数据库密码一样 |
| 失败 | 照旧：`notification_logs` 记一行，不影响主流程，不自动重发 | 没有调度器（决定 5） |
| Edition | 保留 `smtp` 和 `console`，`cloudflare` 只是多一个选项 | 客户自己的主机不一定用 Cloudflare |
| 新模板 | `class_booking_approved`、`class_booking_declined` | 补上面那个缺口 |
| 每个租户的开关 | 默认关。租户在设置里打开后，给家长的邮件才发 | 自动发信是租户对外的行为 |
| 语言 | 先补中文版默认模板，按租户语言选 | 现在只有英文 |

### 动手之前要先定的三件

1. **[动手] 接入发件域名。** Lee 在 Cloudflare 后台把 `pwestudio.online` 接入 Email Sending，确认账户在付费计划上。只有 Lee 能做。
2. **[动手] 建一个 API token。** 权限只给「Email Sending: Edit」。Lee 自己放到生产主机的环境文件里，不经过会话。
3. **[决定] 隐私政策要加一句。** 现在第 5 节写「除加密备份外，我方不会为自身目的将工作室的个人信息传输至境外」（`Privacy_Policy.html:147–148`）。发信会把家长的姓名、邮箱和邮件内容交给 Cloudflare 投递，处理可能在澳大利亚境外。按 `AGENTS.md` §24，这是改变个人信息的使用，要 Lee 定措辞。

另外一件顺手查的事：如果生产现在是 `console`，那五处邮件的内容（含家长姓名、邮箱、电话）正在被打印进应用日志。换成真通道之后这个问题自然消失；在那之前，是否要先关掉打印，也请 Lee 定。
