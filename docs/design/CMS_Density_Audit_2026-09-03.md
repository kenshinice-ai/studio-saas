## 0. 为什么必须实测

`CMS_Roster_Split_Plan.md` 已经证明过一次：两份源文档都把排课页的拥挤归因于
「固定课表那一大块」，**实测发现那块是 `<details>`，折叠态只有 62px**，
真正的罪魁是「添加学员」块。按原诊断优化最多省 62px，问题原样保留。

本轮又撞到同一件事，方向相反：

> `billing.jsx` **1545 行、64 个卡片类**，是 CMS 最大的源文件，静态计数下是头号嫌疑。
> **实测它只有 2 个顶层块、桌面 913px、全部在首屏内 —— 是全站最健康的页面之一。**

**文件大小 ≠ 页面密度。** 静态计数在这一轮会把结论指反。


## 2. 诊断：问题集中在 dashboard，而它是落地页

### 2.1 实测块分解

**桌面 1440×900（总高 2243，5 / 10 块在首屏外）**

| y | 高 | 块 |
|---:|---:|---|
| 0 | 150 | 今日重点（角色工作台） |
| 170 | 209 | TODAY · 今日指挥台 |
| 399 | 152 | 学员专区与作品发布 |
| 571 | **46** | 经营真账（估算）· `<details>` 折叠 |
| 637 | 210 | 今日待办 |
| 867 | **72** | 有待审核的注册申请 ← 首屏边缘 |
| 959 | 210 | 长期未到访 — 12 名学员 |
| 1189 | **78** | 应收 $1963.50 |
| 1287 | **106** | 课时预警 — 2 名学员 |
| 1413 | **722** | 最近操作 |

**手机 390×844（总高 3410，9 / 11 块在首屏外）**
同样的块，但 `学员专区` 涨到 380、`长期未到访` 从 210 涨到 **698**（12 个学员胶囊换行）、
`今日指挥台` 涨到 536。**第一屏只装得下 2 块。**

### 2.2 三个具体的堆叠

**① 「待审核」在同一页出现三次**

| 位置 | 形式 |
|---|---|
| 侧栏 `pending` 导航项 | 带计数徽标 |
| `今日指挥台` 内 | `['待审核', pendingCount, '项', …]` 计数格（`dashboard.jsx:77`） |
| 独立琥珀色条 | 「有待审核的注册申请 · 4 位学员等待审核，点击前往处理」（`:287`） |

三处指向同一个目标页、同一个数字。

**② 四条同形状的琥珀色提醒条被大块隔开**

`待审核`(72) → `长期未到访`(210) → `应收`(78) → `课时预警`(106)
—— 语义完全同类（「有 N 个东西需要你看一眼」），却各自成块、中间还夹着别的内容。

桌面合计 **466px**，手机合计 **986px**。它们是 v5.3 到 v10.7 逐版本累加上去的，
每一条单独看都合理，摞在一起就成了一条提醒的走廊。

**③ `最近操作` 722px —— 落地页最高的块，且与 `logs` 页重复**

`logs` 是独立导航项（实测 29 行、桌面 3098px）。落地页底部再放一段 722px 的摘录，
是这一页最大的单块开销，而且没人会滚到 y=1413 去看它。

## 3. 方案

### 3.1 dashboard 合并「需要注意」区（★★★）

四条琥珀条 + `长期未到访`（共 6 块）合并为**一个区块，每类一行**：

```
需要注意 (4)
  ├ 4 位学员等待审核                        → pending
  ├ 12 名学员有余额但超过 90 天未上课        → students?filter=inactive
  ├ 3 张未付清，其中 2 张逾期 · $1963.50     → billing
  └ 2 名学员余额 ≤ 2 课时                    → students?filter=low
```

每行一句话 + 一个去处，名单点开才展开（`<details>`，默认折叠）。

- 桌面 **466 + 210 = 676px → 约 200px**
- 手机 **986px → 约 240px**
- 顶层块 **10 → 5**

同时删掉 `今日指挥台` 里的 `待审核` 计数格 —— 它和这个区第一行说同一件事。

**注意：这是合并展示，不是删功能。** 每一条的数据源、权限投影、跳转目标都不变。

### 3.2 `最近操作` 从落地页移除（★★★）

`logs` 已是独立导航项。落地页保留一行「最近 N 条操作 →」链接即可。

- 落地页 **−722px**（桌面 −32%，手机 −21%）
- 顶层块再 **−1**

### 3.3 `学员专区与作品发布` 需要一个判断（★★，待确认）

桌面 152px、手机 **380px**，位置在第 3 块 —— 首屏黄金位置。
它的副标题是「点击数字直接处理对应学员」，**看起来是功能入口而不是今日操作**。
如果它不是每天都用，应该降到「需要注意」区下方，或并进 `students`。

**这一条我判断不了使用频率，需要你说。**

### 3.4 `works` 手机 3923px（★★）

全站手机最高的页面（`logs` 4255 是日志，另当别论）。4 个顶层块撑出近 4 屏。
建议：作品网格分页或虚拟滚动，先量清楚是网格本身还是筛选器造成的。
**本轮不出具体方案 —— 需要先按块分解一次。**

### 3.5 `stats` 手机 3 / 7 块在首屏外（★）

`经营月报`(569) + `财务明细报表`(420) + `学员个人分析`(221) 全在 y>844。
这三块是报表，不是概览。建议收进分段控件（与设置页方案 B 同一套 `Tabs` 原语），
默认只展示前 4 块。

### 3.6 `roster` / `students` 的按钮密度（★，观察项）

两页分别 **55 / 53 个可见按钮**，是全站最高。但两页的**块结构都健康**
（roster 名单 y=514 在首屏内，students y=327）。

**这不是排列问题，是每行操作太多。** 建议先做 §3.7 的行内确认，
把「操作按钮 → 确认对话框」这条链缩短，再看是否还需要收纳。
**本轮不动。**

### 3.7 引入行内两段式确认（★★，与 `Learning_From_LetsPaint_CMS` §2.6 同一条）

`再点确认 · 8→7 课时`，3 秒自动解除，不用对话框。
直接减少 roster/students/topup 三页的对话框往返，也顺带解掉
Platform Admin 审计记录的「两套对话框系统」未解决项。

## 5. 顺带发现：浏览器门禁覆盖不到 CMS

`ui_matrix.py` + `ui_matrix.yaml` 是真 Playwright 多视口门禁
（375/768/1280 × 3 语言），但 `pages:` 里**只有三个公开页面**，
没有任何 CMS 页面。

本轮 §1 那张表是手工跑出来的，下次改动后没有任何东西会告诉你它有没有退化。

**建议：把本轮的 12 个 CMS 页面加进 `ui_matrix.yaml`，断言两件事**——
顶层块数不超过阈值、无横向溢出。这比再写一个新脚本便宜得多，
而且 §3 的每一条都会被自动看住。

（`ui_matrix.py` 刻意不进 `verify_local.sh`，因为发布门禁不该依赖浏览器下载 ——
这个决定是对的，不要改。）

## 6. 不建议做的事

- **不要按源文件大小排优先级。** `billing.jsx` 1545 行 / 64 卡片，实测是最健康的页面之一。
- **不要动 `logs` 的总高。** 3098 / 4255px 是 29 行日志的自然结果，它就该长。
- **不要把「需要注意」的四条合并成一条汇总数字。** 它们跳向四个不同的页面，
  合成一个数字就没法点了。合的是**块**，不是**信息**。
- **不要在本轮碰 roster/students 的按钮数。** 块结构是健康的，先做 §3.7 再看。
