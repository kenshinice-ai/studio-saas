# StudioSaaS 使用者视角复盘与优化方案

日期：2026-09-06 · 对应版本：v10.15.0 · 范围：UI/UX、易用性、功能完整性
明确不在范围内：安全、代码质量、架构重构

---

## 0. 这份文档是怎么做出来的

1. 通读 `AGENTS.md`、`docs/Product_Surface_Model.md`、`docs/Design_System.md`，先搞清产品自己声称的边界与承诺。
2. 把仓库里已生成的静态页面拼成一个可访问的站点，**真的用浏览器打开了**：产品营销站、租户门户、快速报名、公开课表、CMS 宿主页、Studio Admin 登录页。
3. 逐条回到源码核实所见现象，确认是产品行为而不是预览环境的假象。

**必须说明的局限**：本地没有 PostgreSQL、后端未启动，因此**登录态下的 CMS 与 Studio Admin 内页没有实际操作过**，这两块的结论来自源码阅读，标注为「源码判断」。凡是我看到过界面的，标注为「已实测」。

同样要说明：**有三条我一开始认定的问题，核实后不成立**，已记入第 8 节。写在这里是为了避免有人重复走一遍。

## 1. 总体判断

这个产品的完成度远高于它的外表所暗示的程度。四个界面的职责切分是清楚的，`Product_Surface_Model.md` 里那张表在代码里是真的被遵守的；主题系统不是配色表而是按对比度反解出来的生成器；快速报名页是我见过的同类产品里做得相当克制、相当好的一个。源码注释里保留了大量「上一版为什么错」的记录，这在小团队产品里很罕见。

问题不在于「做得糙」，而在于**几个方向性的默认值站错了边**，以及**大量精力投在了单次转化面（营销站、门户），而每天用八小时的运营面（CMS）在几个关键的失败路径上是裸的**。

一句话：**这个产品对「一切正常时的第一次访问」打磨得很好,对「出问题时的第两百次使用」几乎没有设防。**

## 2. 必须优先处理的四件事

这四条不是「可以更好」，是「现在就在伤人」。

### P0-1 · 三个后台默认中文，与产品自我定位直接冲突

**已实测。** 用一个全新的浏览器打开 Studio Admin 登录页，整页是中文。

原因在 `backend/frontend/assets/i18n-runtime.js:45`：

```js
let language = localStorage.getItem(STORAGE_KEY) === 'en' ? 'en' : 'zh';
```

没有 `navigator.language` 探测，没有服务端语言协商。**只要用户没手动切过，就是中文**。这条逻辑同时管着 Studio Admin、Super Admin 和 CMS。

而与此同时，租户公开门户是会自动探测的（`tenant-template/index.html:1090` 读 `navigator.languages`）——我打开租户门户看到的是英文，打开后台看到的是中文，**同一台机器、同一个浏览器、同一分钟**。

再对照产品营销站自己写的 meta（`product-home.html:24`）：

> "Studio software for art, music and dance schools in Australia."

一个墨尔本的画室老板，被一个英文落地页说服，注册，点进 Studio Admin，看到一整页中文。语言开关在右上角，但它此刻正被一个中文报错气泡压住（见 P0-4 的截图场景）。

还有一层结构性的怪异：**两个后台的翻译方向是相反的**。Studio Admin / Super Admin 的源码字符串是英文，`admin-i18n.js` 做 en→zh；CMS 的源码字符串是中文，`cms-i18n.js` 做 zh→en。也就是说英文用户在 CMS 里看到的是机器词典的产物，中文用户在 Studio Admin 里看到的是机器词典的产物，**没有任何一个语言的用户拿到的是全套原文**。

**改法**（约半天）：

1. `i18n-runtime.js` 的初始值改为三级回退：`localStorage` → 服务端下发的租户默认语言 → `navigator.languages` → `zh`。
2. 租户在 Super Admin 开户时就带一个 `default_locale`，随 `/brand` 下发。这是真正的解——语言应该跟着**工作室**走，而不是跟着浏览器 localStorage 走（前台三个人共用一台机器，一个人切了所有人都变）。
3. 语言开关从「右上角一个小胶囊」提升为登录页上的显式一等控件。登录页是唯一一个用户还没有任何上下文的时刻，也是唯一一次值得让他明确选语言的时刻。

### P0-2 · CMS 没有错误边界，任何一个 JS 异常都会把整个后台变成白屏

**源码判断，但证据是确定的。**

```
grep -rn "ErrorBoundary|componentDidCatch|getDerivedStateFromError" legacy-root/src/
→ 无任何命中
```

`legacy-root/index.html:1270` 只有一行 `<div id="root"></div>`，没有兜底内容，没有 `<noscript>`——顺带一提，**五个界面的 HTML 里 `noscript` 出现次数都是 0**（门户、报名、Studio Admin、Super Admin、产品站）。

这意味着：前台在录一张 800 块的发票，`billing.jsx` 里某个字段是 `null` 而代码读了它的属性 —— 整个 CMS 白屏，输了一半的表单没了，屏幕上没有任何字告诉她发生了什么、该怎么办。她只能猜「是不是要刷新」。

一个 4180 行主文件 + 十六个 panel、每天被非技术人员用八小时的 React 应用没有错误边界，这是最不成比例的风险敞口。

**改法**（约一天）：

1. 加一个顶层 `ErrorBoundary`，兜底界面必须做到三件事：说人话（「这个页面出问题了，你刚才的操作可能没保存」）、给一个「返回工作台」的出口、给一个可复制的错误编号（配合 `logs`）。
2. 每个 panel 外面再包一层。目标是**一个 panel 崩掉时侧栏还在**，用户能走到别的地方去，而不是整个应用消失。
3. `index.html` 里补一段静态兜底：脚本没加载出来时至少显示「正在加载 Studio CMS…如果这行字一直在，请检查网络后刷新」，而不是一片米色空白。

### P0-3 · 会话过期时 1.5 秒后强制登出，填到一半的内容直接消失

**源码判断。** `legacy-root/src/cms-app.jsx:953`：

```js
if (r.status === 401) {
    showToast('登录已过期，请重新登录 / Session expired', 'error');
    setTimeout(doLogout, 1500);
    return false;
}
```

场景：前台在柜台给家长办充值，选学员、填金额、勾了开发票、正在核对税码。家长掏手机付款，中间聊了两句。她点「确认」，token 已过期 —— 一个一闪而过的 toast，1.5 秒，登出，全部重填。家长还站在她面前。

对比：Studio Admin 是有脏状态保护的（`studio-admin.js:4225` 有 `beforeunload`，`:945-959` 有一条 dirty/clean 状态栏）。**CMS 里搜不到任何 `beforeunload`**。做得更细致的是那个一天开一次的品牌编辑器，被保护得最差的是那个一天开两百次的收银台。

**改法**（约一天半）：

1. 401 不要登出，改为**原地弹一个重新登录的浮层**。密码验过之后关掉浮层，用户回到刚才那一屏，数据还在。这是唯一真正解决问题的方案。
2. 过渡方案（半天可上）：登出前把当前正在编辑的表单状态写进 `sessionStorage`，重新登录后恢复并提示「已恢复你上次未提交的内容」。
3. 给 CMS 补 `beforeunload`，标准与 Studio Admin 对齐。
4. 顺带：一个 1.5 秒的 toast 承载不了「你要重新登录了」这种级别的消息。这类消息应该是一个需要用户点掉的对话框。

### P0-4 · 后端抖一下，家长看到的门户首屏被五条报错横幅盖住

**已实测。** 后端不可达时打开租户门户，页面顶部叠了五条横幅：

```
Navigation status could not be confirmed; the page is showing only locally ready content.
Brand details are temporarily unavailable; default content is shown.
Course details are temporarily unavailable. Please retry later.
The public gallery is temporarily unavailable.
Selected work is temporarily unavailable. Please try again later.
```

工作室名字被横幅从中间划过，Hero 标题被推出视口。每条右边一个 `×`，**没有一条提供「重试」**。

机制在 `tenant-template/index.html:1261` 的 `showSurfaceStatus()`：按 `source` 去重后 `box.appendChild(note)`——五个数据源就是五条。容器是 `position:fixed; top:74px; display:grid`（:541），横幅向下堆叠，压在内容上。

这是家长第一次接触这家工作室的页面。五条英文技术报错，等于告诉他「这家机构的网站坏了」。而实际上页面**是可用的**——报名按钮好好的，静态内容都在。

注释里写着这个设计的来历（:538）：以前唯一的那条提示藏在导航后面看不见，所以改成了「可关闭的堆叠」。方向对，但从「看不见」直接跳到了「盖住首屏」。

**改法**（约半天）：

1. 全页合并成**一条**。多个源失败时只说一次：「部分内容暂时无法加载，正在重试。」
2. 位置从「盖住首屏」改成「贴在导航条下方、占位而不覆盖」，或者干脆做成一个不打断阅读的角标。
3. 加自动重试（退避到 3 次），成功后横幅自己消失。**用户什么都不用做**才是这里的正确交互。
4. 分级：`brand` 失败（页面在用默认品牌）值得告诉访客；`gallery` 失败其实只需要在那个区块里就地显示，不必占用全局横幅。

顺带一个对照：公开课表页的降级提示是**一行灰色小字排在标题下面**（已实测），完全不打扰。同一个产品的两个公开页，同一类问题，两种处理方式，好的那个没有被复用。

## 3. 逐界面

### 3.1 产品营销站

**已实测。** 视觉水准是这四个界面里最高的：衬线大标题、纸质底色、右侧那张「一个系统四个界面」的等距空间图确实把产品结构讲清楚了，比十行文案有效。

**问题一：首屏代价与它承担的说服任务不成比例。**

| 资源 | 体积 |
|---|---|
| `product-spatial-three.js` | 549 KB |
| `living-studio-system-poster-light.webp` | 245 KB |
| `living-studio-system-poster.webp` | 171 KB |
| `product-home.html` | 47 KB |

海报是静态降级用的，Three.js 是增强用的。降级链路本身写得很规矩（reduced-motion / data-saver / 移动端 / WebGL 失败都有分支）。但值得问一句：**这个可交互的 3D 场景，比那张已经很好看的静态海报，多说服了多少人？** 如果答案是「不确定」，那 549 KB 就应该先关掉做个 A/B，而不是默认开着。

**问题二：没有自助试用入口。** 主 CTA 是 "Book a walkthrough 预约演示"。这对高客单价 B2B 是成立的，但它把所有线索都压到了人工跟进上。至少应该有一条并行的路：一个不用留联系方式就能点进去乱按的 demo 租户。仓库里已经有 `lets-paint-showcase` 和 `music-studio-showcase` 两个展示租户了，**能力已经具备，只差把它放到首屏当第二 CTA**。

**问题三：给不了「这东西适合我吗」的答案。** 页面讲的是系统结构（四个界面如何连接），但一个琴行老板的问题是「我有 60 个学生、3 个老师、微信收款，你能替掉我现在的 Excel 吗」。缺一个「按规模/按行业」的自我对号入座区块，缺客户案例，缺具体数字。

### 3.2 租户公开门户

除 P0-4 外：

- **`tenants/lets-paint-studio/index.html` 是 165 KB 单文件**，内联了全部 CSS 与逻辑。家长在 4G 下点开微信链接，首屏要吞这么多字节。好处是没有额外往返，坏处是没有任何缓存复用——同一个访客第二次打开还是 165 KB。值得把内联 CSS 抽成一个带 `immutable` 缓存的独立文件（后端已经有 `_stamp_asset_versions` 的内容摘要机制，基础设施是现成的）。
- **语言切换按钮是右上角一对 13px 的小胶囊「中 / EN」。** 对一个中文母语的家长，「EN」两个字母很好认；对一个英文母语的家长，「中」是一个他不认识的字形。至少加上 `aria-label`，更好的做法是显示目标语言的自称（`中文` / `English`）而不是缩写。
- **空态没有出口。** 一个刚开业、还没发布任何作品的工作室，门户上的作品墙是什么样？这决定了新客户上线第一周敢不敢把链接发出去——这恰恰是他最想发链接的一周。

### 3.3 报名流程 —— 这块做得好，不要动

**已实测，这是全产品体验最好的一页。**

- 只要三个字段（姓、名、手机）就能提交，其余折叠在「Add more details (optional)」后面。
- 左侧一句话说明「留下资料，工作室会为你安排合适的班次和时间」——先告诉用户接下来会发生什么，再要他填东西。
- 同意条款是一句人话，不是法律文本，旁边有「Read the privacy note →」可展开。
- 主按钮一个，通栏，没有竞争项。

唯一建议：**提交成功之后的那一屏值得再投入一点**。家长最想知道的是「多久会有人联系我」。给一个具体承诺（「我们会在 1 个工作日内电话联系你」）和一个可截图的回执编号，比一句「提交成功」有用得多。这个数字应该由工作室在 Studio Admin 里自己填。

### 3.4 公开课表与作品展示

**已实测。** 课表页在没有已发布课程时显示：

> No classes are published at the moment.
> Back to the studio website →

排版干净，但这是**一条断头路**。一个家长专程来看课表，看到「暂无」，然后被请回首页。此刻他的意图是全站最明确的——他想上课。

**改法**（约半天）：空态里放一个「新班开课时通知我」的迷你表单（姓名 + 手机，复用报名 API，`source` 标 `timetable_waitlist`）。这条线索直接进 CMS 待处理队列。**同一屏的空态，从流失点变成转化点。**

### 3.5 Studio CMS —— 每天用八小时的那个

除 P0-2、P0-3 外：

**导航结构本身是合理的。** `cms-app.jsx:3231` 的四组十二项（今日 / 教学运营 / 经营 / 记录）分法清楚，`cmsPageTitle` 从 `NAV` 派生而不是另写一张表（注释里记着两者曾经漂移过），这个决定是对的。

**移动端底部导航的图标槽是空的。**

```js
{k:'dashboard',i:'',s:'工作台'}, {k:'roster',i:'',s:'课表'},
{k:'students',i:'',s:'档案'},   {k:'topup',i:'',s:'充值'}
```

`i` 是空字符串，而模板里 `<span className="text-[22px] leading-none">{i}</span>` 照样渲染。结果是 52px 高的标签栏里，每一项上方有一块 22px 的空白，下方一行 10px 的字。「更多」抽屉里七项中有六项同样是空图标。

老师在教室门口单手举着手机点名，看的是 10px 的字。**这是全产品可感知性价比最高的一处修复**——`Icon` 组件已经存在、桌面侧栏已经在用（`i:'dashboard'` / `i:'calendar'` / `i:'users'`），把桌面那份图标名填进移动端这四行就行。约一小时。

**没有列表虚拟化。**

```
grep -rn "virtual|react-window|IntersectionObserver" legacy-root/src/ → 无命中
```

300 个学员的名单、上千条操作日志全部一次性挂进 DOM。日志页有分页兜住，学员页有分页兜住，但学员页的**筛选与排序是在全量数组上做的**，且 CMS 顶着一个全局 MutationObserver 翻译层——每次 React 重渲染，观察器都要重新扫一遍新增节点。规模上去之后这两者会互相放大。

**只有一个快捷键。** `cms-app.jsx:634` 的 ⌘K 全局搜索。一个前台每天重复几十次「今天 + 某个班 + 全部签到」，值得有键盘路径。建议至少补：`g` + 首字母跳转（`g r` → 课表、`g s` → 学员）、列表里 `↑↓` 移动 + `Enter` 打开、弹窗 `Esc` 关闭（先确认全部弹窗都支持）。

**空态覆盖不均。** `students.jsx:101` 用的是共享 `EmptyState` 组件，文案也写得好（「没有姓名、电话、微信或邮箱包含「X」的学员。换个关键词，或清空搜索看全部。」——给了原因也给了出路）。但 `dashboard.jsx`、`topup.jsx`、`progress_reports.jsx` 三个文件里搜不到任何空态字样。**工作台是新用户第一眼看到的页面**，它在零数据时的样子无人设计。

**没有任何首次使用引导。**

```
grep -rn "onboard|新手|checklist|向导|wizard" legacy-root/src backend/frontend/…
→ 唯一命中是 Super Admin 里 "onboarding" 这个租户生命周期状态名
```

一个老板拿到账号的第一天，登录进来面对十二个空面板。他要建课程、建班次、导学员、配充值套餐、设课酬规则、然后去 Studio Admin 配网站——**没有任何东西告诉他这个顺序，也没有任何东西告诉他进行到哪一步了**。

这是**留存问题，不是体验问题**。仓库里已经有 `customer-resources/PWE_Studio_Data_Import_Template.xlsx` 和 142 KB 的 `manual.html`，材料齐全，但它们都在产品外面。

**改法**（约两到三天，是本文档里投入产出比最高的一项）：工作台顶部放一张开通清单卡，六到八步，每步一个直达按钮，完成状态从真实数据推导（有课程了？有学员了？发布过网站了？），全部完成后卡片自己消失。

### 3.6 Studio Admin

**已实测（仅登录页）。**

登录页在**用户还没做任何操作时**同时显示两条报错：右上角一个红色气泡「请填写工作室网址标识后继续。」，表单里一块红底提示「尚未选择工作室。请从你的工作室网址打开本控制台：/<工作室网址标识>/studio-admin。」

三个问题叠在一起：

1. **报错先于操作。** 用户什么都还没做就被判了两次错。这两条应该是提示（灰色说明），不是错误（红色）。
2. **同一件事说两遍**，而且两遍的措辞不一样。
3. **术语是开发者的，不是老板的。**「工作室网址标识」「/<工作室标识>/studio-admin 里的那一段」——老板脑子里这个东西叫「我的网址」。他手上有的是一条完整链接。

**改法**（约半天）：字段标签改成「你的工作室网址」，占位符给完整形态 `pwestudio.online/你的工作室`，并且**接受粘贴整条 URL 然后自己解析出 slug**。这一条改动能消灭这个页面上大部分的求助。页面加载时不报错，只在提交时校验。

**源码判断的一条好消息**：Studio Admin 的草稿保护是这个产品里做得最好的——`studio-admin.js:945-959` 有一条 dirty/clean 状态栏（"No unsaved changes" / "Published version X"），`:4225` 有 `beforeunload`。这套东西应该被搬到 CMS 去（见 P0-3）。

### 3.7 Super Admin

**源码判断。** `super-admin.js` 里有 3 处裸的 `window.confirm`，其中 `:3815`：

```js
&& !window.confirm(planImpactWarning(affected.length, over, showcaseReduced))) return;
```

**改套餐、且已经算出了会影响多少个租户、有多少超限**——这么重的一个商业动作，确认界面是浏览器原生的灰框弹窗，里面塞一段拼出来的长文本，两个按钮叫「取消 / 确定」。原生弹窗没法排版、没法高亮受影响的租户数、没法列出具体是哪几个、没法要求二次确认。

另外两处（`:88`、`:121`）是 "Discard unsaved changes?" ——这条是英文硬编码，不走 `admin-i18n`，所以**中文界面下会突然弹出一句英文**。

**改法**（约半天）：换成产品内的确认对话框，把 `planImpactWarning` 里那几个数字做成结构化展示（受影响租户数、超限数、被削减的展示位），高危项要求输入租户数量或勾选确认。

## 4. 横向问题

### 4.1 双语：机制选错了层

除 P0-1 的默认值问题外，还有一个更深的问题：**CMS 的英文不是翻译出来的，是在 DOM 上事后替换出来的。**

`i18n-runtime.js` 挂一个 `MutationObserver`，React 渲染完中文之后再把文本节点替换成英文。这个做法的代价：

**第一，词典覆盖不全就直接漏中文。** 用脚本剥掉注释后统计源码里会显示给用户的中文串，约 1519 条；`cms-i18n.js` 词典 861 条。**大约一半的界面文案没有对应英文条目**，落回中文（这个数字是粗略估计——提取会把模板字符串片段算进去——但量级是可信的）。而且漏的往往正是最长、最需要读懂的那些：

> 「发现下列可能是同一名学员的既有档案。并入会把这次报名归到既有学员名下（初始课时也入其账本）；确认是新学员则继续新建。不会自动合并。」

这条判重说明决定了一次不可逆的数据合并。一个英文用户在这里看到的是一整段他读不懂的中文，然后要做一个不可撤销的决定。

**第二，拼接句子必然漏翻。** 词典按整句匹配，而代码里大量这种：

```js
`批量签到确认 · ${fmtDate(rDate)}：${futureWarning}排课 ${ids.length} 人；已签到 ${already} 人；余额不足 ${insufficient}`
```

带变量的句子没有稳定的键，永远不会被命中。

**第三，先中后英的闪烁。** 观察器在 React 渲染之后跑，所以每次列表更新，英文用户理论上都会看到一帧中文。

**建议**：不要试图把词典补到 100%——那是一场追不上的赛跑。分两步走：

1. **短期**：按「后果严重度」而不是「出现频率」补词典。所有确认对话框、所有错误提示、所有涉及钱和不可逆操作的说明，必须 100% 覆盖。其余的漏了就漏了。
2. **中期**：新写的代码一律走 `t('key')`，不再写中文字面量。存量按 panel 逐个迁移，从 `billing.jsx` 和 `topup.jsx`（钱）开始。观察器保留为过渡期的兜底，迁移完再删。

另外，本地化不止是 UI 文案：日期、货币、数字格式、姓名排序也需要跟着语言走。源码注释提到日期统一输出 `DD/MM/YYYY`（澳洲格式）——这对中文用户是陌生的，对美国用户是会读错的。

### 4.2 性能：CMS 首屏 1.4 MB，其中 441 KB 是浏览器里的 CSS 编译器

`backend/vendor/README.txt` 写得很明确：

> `tailwindcss.js` — tailwind play build 3.4.16

**生产环境装的是 Tailwind Play CDN 版**，也就是那个「在浏览器里现场编译 CSS」的开发用构建。它在 `legacy-root/index.html:183` 同步加载，排在 React 前面。

CMS 首屏账单：

| 资源 | 体积 |
|---|---|
| `cms-app.js` | 711 KB |
| `vendor/tailwindcss.js`（浏览器端 JIT 编译器） | 441 KB |
| `react` + `react-dom` | 142 KB |
| `legacy-root/index.html`（含内联样式与桥接逻辑） | 66 KB |
| `cms-i18n.js` | 66 KB |
| `i18n-runtime.js` | 10 KB |
| **合计** | **≈ 1.44 MB** |

老师在教室的 4G 下打开 CMS 点名，要先下 1.4 MB，然后等浏览器把 Tailwind 类现场编译成 CSS，然后 React 才挂载。中间没有骨架屏，没有加载文案——`<div id="root"></div>` 是空的。

按每 KB 收益排优先级：

1. **构建期出 Tailwind CSS，删掉那 441 KB 的运行时编译器。** 一次构建改动，砍掉 30% 首屏体积并去掉一段阻塞渲染的 CPU 工作。这也顺带解决了 `legacy-root/index.html` 里那两百多行 `[class*="bg-indigo-8"] { … !important }` 的覆盖层——那些覆盖之所以存在，正是因为要在运行时追着 JIT 的产物打补丁，注释里记录了它反复回归过三次（:999、:1153、:1177）。
2. **按 panel 拆包。** 711 KB 里，`billing.jsx`（1545 行）+ `integrations.jsx`（547 行）+ `private_lessons.jsx`（546 行）+ `finance.jsx` 加起来占很大一块，而一个老师**从不打开这几个页面**。按 tab 懒加载，老师的首屏能砍掉一半以上。
3. **`cms-i18n.js` 66 KB 只在英文模式下需要。** 中文用户白下。挪到语言切到英文时再加载。
4. **门户 165 KB 单文件的内联 CSS 抽出去**，让回访命中缓存。

### 4.3 移动端

除了 4.2 的体积和 3.5 的空图标：

- 底部标签栏 `min-h-[52px]`，加上 `env(safe-area-inset-bottom)` 处理是对的，iPad standalone 的安全区也考虑到了（`cms-app.jsx:3745` 附近有注释记录）。这块基础不差。
- 「更多」抽屉里七项排成 `grid-cols-4` 两行，第二行只有三个，右下角空一格。同时抽屉里的按钮**没有 `aria-current`**，而底部四项有——同一套导航两种无障碍处理。
- 学员档案是个信息量很大的弹窗（`student_profile.jsx` 494 行 + 多个 tab）。在手机上这种「弹窗里放多标签页」的结构通常很难用。**这一条我没有实测**，但值得作为一次真机走查的首要目标。

### 4.4 视觉一致性

主题系统是真的：`legacy-root/index.html:265` 起，Tailwind 的 `indigo` / `violet` / `fuchsia` 等色系被重新指向 `var(--accent)` 等语义令牌，`palette_gen.py` 对 15 个主题模式跑 390 条对比度断言。这套东西在同类产品里属于做得相当认真的。

问题在于**它是靠一层脆弱的覆盖维持的**。`index.html` 后半段有两百多行专门处理「JIT 没能重指的那些类」，注释里逐条记录了失败史：侧栏 `bg-indigo-900` 没被映射所以在任何主题下都是一片靛蓝；`active:bg-indigo-800` 解析成了 `var(--ink)`；`after:bg-indigo-600` 的下划线把自己的按钮填满了。这些都修好了，但**它们会再回来**——只要有人在 panel 里新写一个没被映射到的 Tailwind 色阶。

这不是「现在有 bug」，是「这个机制保证了以后还会有 bug」。第 4.2 节的构建期编译能连带解决它：编译期能拿到全部类名，可以直接在构建时报错。

另一个观察：**产品营销站的视觉水准明显高于三个后台。** 营销站是衬线大标题、纸质肌理、精心构图的空间插画；CMS 是标准的 Tailwind 后台。落差本身不是问题（AGENTS.md 明确写了运营界面不引入营销动效，这个原则是对的），但一个被营销站说服的老板，进入产品第一天会经历一次期待落差。缩小落差不需要动效，只需要把营销站的**排版克制**——那套字号阶梯、那种留白节奏——带一点到后台的标题层级里。

## 5. 缺的不是打磨，是功能

以下几条在仓库里搜不到实现，属于「没有」而不是「做得不好」：

| 缺失 | 为什么重要 | 谁在承担代价 |
|---|---|---|

## 7. 不要动的地方

复盘容易变成「哪哪都得改」。以下几处是明确做对了的，改动时请绕开：

- **快速报名页的表单设计**（三个必填 + 渐进展开 + 人话同意条款）。这是全产品最好的一屏。
- **`NAV` 单一来源**：页面标题从导航派生而不是另写一张映射表。注释记录了两者曾经漂移，这个修复是对的。
- **`palette_gen.py` 的生成式配色**：不要手改任何一个十六进制值。
- **Studio Admin 的 dirty/clean 状态栏 + `beforeunload`**：这是正确的范式，应该被复制到 CMS，而不是被简化。
- **CMS 用自定义 `ConfirmDialog` 而非 `window.confirm`**（`cms-app.jsx:570`）。注释记录了消灭最后一个裸 `window.confirm` 的过程，这个方向是对的——只剩 Super Admin 那三处待清理。
- **公开课表的降级提示样式**（一行灰色小字）：这是门户横幅应该抄的那个样子。
- **源码里那些「上一版为什么错」的中文注释**。它们在这次复盘里帮我避开了至少三个错误结论。

## 8. 核实后不成立的三条

写在这里，是为了别人不必重走一遍。

**「CMS 里有 2197 处硬编码 Tailwind 颜色类，绕过了设计令牌。」**
数字是真的，结论是错的。`legacy-root/index.html:265` 起把 Tailwind 的色系重新指向了 `var(--accent)` 等语义令牌，`bg-indigo-600` 在运行时解析的是租户主题色。真正的问题是这层重指靠两百多行 `!important` 覆盖维持，反复回归过——已作为第 4.4 节写出。

**「产品营销站把中英文挤在同一个导航里（`Why痛点` `Pricing定价`）。」**
这是我的预览环境造成的假象。`product-home.html:11` 写着所有 `data-lang` 元素在服务端下发前会被按语言剔除。我起的是静态文件服务器，没有这一步。生产环境上是干净的单语页面。

**「Studio Admin 的长设置表单没有未保存保护。」**
有。`studio-admin.js:4225` 有 `beforeunload`，`:945-959` 有 dirty/clean 状态栏。**反过来才是问题**——没有这层保护的是 CMS，已作为 P0-3 写出。
