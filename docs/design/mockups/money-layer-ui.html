PWE Studio界面方案 · v10.1

界面方案 · 只做设计，等你定Interface proposal · design only

34 条接口，2 个新导航项34 endpoints, 2 new nav items

v10.0.0 的钱这一层已经上线，但只有 API。这份方案把它放进现有的三个界面 —— 而关键判断是：它不需要一个新界面，也几乎不需要新导航。 The v10.0.0 money layer is live, but only as an API. This proposal places it into the three existing surfaces — and the key judgement is that it needs neither a new surface nor, almost, any new navigation.

01

先看现状：CMS 左栏已经是分组的Where things already are

这不是一块白板。CMS 的左栏早就分好了四组 —— 今日 / 教学运营 / 经营 / 记录 —— 而「经营」组里已经有「充值与退款」和「经营统计」。钱的功能有天然的家，不需要另起炉灶。

This is not a blank slate. The CMS rail is already grouped into four clusters — Today / Teaching / Business / Records — and the Business cluster already holds top-ups and business statistics. The money layer has a natural home; it does not need a new one.

Studio Admin 的 12 个面板全部是公开网站与品牌（品牌 / 首屏 / 作品 / 课表 / 报名 / 常见问题…）。Platform Admin 是「租户与订阅 / 套餐与定价」的主从结构。三个界面的边界本来就清楚，方案只需要尊重它。

Studio Admin's twelve panels are all about the public website and brand. Platform Admin is a master–detail over tenants, subscriptions, plans and pricing. The three surfaces already have clear boundaries; the proposal only has to respect them.

一条克制One restraint

我没有把「账单」和「充值与退款」合并。它们看起来像一件事，其实是两本账：充值动的是课时，账单动的是钱。产品的数据模型刻意让它们分开且互相对得上；界面如果合并，第一次出现「余额 3 节课 / 欠费 $220」这种组合时，前台就不知道该看哪个数了。

Billing and Top-ups are deliberately not merged. They look like one thing and are two ledgers: a top-up moves lessons, an invoice moves money. The data model keeps them separate and reconcilable on purpose; merging them in the interface would leave the front desk unsure which number to trust the first time an account reads "3 lessons left / $220 owing".

账单工作区The billing workspace

一个页面回答三个问题：谁欠钱、这张单是什么、钱到了没有。左边是列表（38.2%），右边是选中的那张单（61.8%）—— 这是 --ui-golden-columns-reverse，因为详情才是主体，列表是导航。

One page answers three questions: who owes, what this invoice is, and whether the money arrived. The list takes 38.2% and the selected invoice 61.8% — --ui-golden-columns-reverse, because the detail is the subject and the list is navigation.

三处刻意的设计：「编辑」是灰的且带叉——已开具的发票不可改是数据库触发器保证的，界面必须诚实地表现这条约束，而不是给一个点了会报错的按钮；列表带多选和「批量发出」——周期账单一次生成几十张草稿，逐张点是不可用的；「这张单发生过什么」直接读 invoice_events，包括推送 Xero 的结果，因为家长说「我没收到」时这是唯一能回答的地方。Three deliberate choices. Edit is greyed with a cross: an issued invoice is immutable by database trigger, and the interface should say so rather than offer a button that errors. The list is multi-select with bulk issue, because a term run drafts dozens at once. And the event log reads invoice_events including the Xero push, because it is the only place that can answer "we never got it".

04

课酬：四个数必须同屏Teacher pay: four numbers, one screen

老师看到「本期 $1,240」会问的第一句是「我记得比这个多」。所以界面不给一个数，给四个：排了多少 / 实际上了多少 / 请假按政策计费多少 / 老师取消不计费多少。差异逐条可点开。争议在发钱之前解决，而不是之后。

A teacher shown "$1,240 this period" asks "I thought it was more" first. So the screen does not show one number, it shows four: scheduled, actually taught, charged-absent under policy, and teacher-cancelled unpaid. Every difference opens. Disputes get settled before anyone is paid.

05

Xero：三个开关，界面上也必须是三处Xero: three switches, three places

权利在平台侧，连接和推送在租户侧。如果界面把它们并成一个开关，加购到期就会顺手断开连接，换会计看起来像退订 —— 后端已经把它们分开了，界面不能又合回去。

Entitlement is platform-side; connection and pushing are the studio's. If the interface merges them, a lapsed add-on silently disconnects and changing accountant looks like cancelling. The backend keeps them apart; the interface must not put them back together.

08

我刻意没做的What I deliberately did not do

没做「财务」一级菜单No top-level Finance section

把账单、课酬、报表收进一个新的一级入口，会让前台每天多点一层。它们分属「经营」组里的不同日常动作Folding billing, pay and reports behind one new entry adds a click to every day. They are different daily actions inside one existing cluster

没合并账单与充值Billing and top-ups stay apart

课时账与钱账是两本，数据模型刻意分开。界面合并会让「3 节课 / 欠 $220」无法解读Two ledgers, separated on purpose. Merged, "3 lessons / $220 owing" becomes unreadable

没给已开发票加「编辑」No edit on an issued invoice

触发器会拒绝。界面给一个点了报错的按钮，比不给更糟The trigger refuses. A button that errors is worse than no button

没做报表生成器No report builder

四张固定报表覆盖 90% 的问题；生成器是另一个产品Four fixed reports cover 90% of the questions; a builder is a different product

没在 Studio Admin 放钱No money in Studio Admin

那 12 个面板是「我的网站长什么样」。唯一例外是发票外观，因为那确实是品牌Those twelve panels are about the website. The one exception is invoice appearance, which genuinely is brand

没做深色模式No dark mode

console-theme.css 写着 light only：控制台在白天用，深色留给家长夜里看的公开页console-theme.css is light-only by design: consoles are worked in daylight; dark is for the public page a parent opens at night

09

要你拍板的Decisions for you

  1. 两个新导航项叫什么？我用了「账单」和「课酬」。备选：「收费」/「财务」、「老师课时」/「工资」。术语一旦进界面就会进客户嘴里，改起来贵。
  2. What do the two new nav items get called? I used Billing and Teacher pay. Terminology entering the interface enters the customer's vocabulary, and is expensive to change later.
  3. 成长报告放「待处理」还是自己一项？我放进了待处理的第三个标签，因为它确实是等人做的事；但如果你觉得它值一个独立入口，那是第三个新导航项。
  4. Progress reports: inside Pending, or their own item? I put them as a third tab in Pending because they are work waiting for a person — but they could justify their own entry.
  5. Xero 加购定价渲染图里写了 $19/月，这个数还没定。
  6. Xero add-on price — the mockup says $19/month; that number is not decided.
  7. 先做哪一块？我的建议是账单工作区——它是唯一一个「不做就等于 API 白写」的部分，其余都能靠现有页面先撑一阵。
  8. Which first? My recommendation is the billing workspace: it is the only piece whose absence makes the API useless, while the rest can wait behind existing pages.
