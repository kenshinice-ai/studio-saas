## 1. 深色变亮 —— 确认要做

纸的感知明度 L\* 只有 7 左右，接近纯黑。改生成器深色锚点的一个数字，
面板、线条、状态色按现有关系自动跟着走，**1080 条对比度断言自动重跑**。

有一件事要一起看，否则会白改：**深色变亮之后，对比度是往下走的。**
纸抬到 L\* 12–14，墨还是那个墨，正文对比度会从现在的水平掉一截。
所以这不是"改一个数就完"，是"改一个数，然后让求解器重新解一遍墨和线"。
好在这正是生成器的职责，也正是那 1080 条断言存在的意义——**改完不达标它
会直接红，不需要用眼睛判断**。

半天，随课表那一版发。

## 2. 后台先做完整 —— 字段清单

你列的五项，加上我上一轮提的两项必须项：

| 字段 | 存在哪 | 备注 |
|---|---|---|
| 课程内容 | `class_schedules.course_id` **已有列，但从没被写过** | CMS 加课程下拉；没选就退回 `label` |
| id | `class_schedules.id`（uuid，已有） | **建议不对外暴露**，见下 |
| 教师指定 | 新列 `teacher_user_id` | `/tenant/team` 已经能列出 teacher |
| 展示几周 | `website_profile.timetable_weeks` | 1–4，默认 2 |
| 停课 | 新表 `class_schedule_exceptions` | 上一轮 §2，我的立场没变：**必须做** |
| 公开与否 | 新列 `is_public`，默认 false | 上一轮 §1.1 |
| 地点 | 新列 `room` | 选填 |

### 2.1 关于 id：建议不要放到公开接口里

内部 uuid 不是机密，但**放出去就变成了一个承诺**——一旦有人拿它做书签或
外链，我们就不能再重建这条记录。公开课表 v1 没有单节课的深链需求，
所以对外用 `日期 + 开始时间` 定位就够了，uuid 留在后台。

（如果以后要做「这节课的报名链接」，那时再发一个**专门的公开 id**，
而不是把内部主键翻出来。）

### 2.2 一个会被现有逻辑绊到的地方：冲突检查

CMS 现在有 `schedOverlap()`，只比 **weekday + 时间**。加了老师之后，
这个检查同时**变得太松也变得太紧**：

- **太松**：同一个老师被排到两个同时段的班——真正的冲突，现在不报。
- **太紧**：两个班同一时间但不同老师、不同教室——完全正常，现在会报。

所以加 `teacher_user_id` 的同时，冲突判定要改成：**同老师 + 时间重叠**才算
冲突；没指定老师的沿用现在的行为。否则一间有两位老师的工作室，
每排一节课都要点一次「仍要保存」，很快就学会无视这个提示——
**一个总是误报的警告等于没有警告。**

## 3. 门户显示：给统一建议值，不给一堆开关

**我的建议：不做逐字段的显示开关。只留两个，而且两个都不是"审美偏好"。**

### 为什么不做开关

这个产品刚刚走完一轮相反方向的路：八套行业配色、43 个 token、
每个界面自己声明颜色——**修法都是收敛**。`Design_Constraints` 第 0 条就是
「优雅是收敛的产物，不是 43 个正确 token 的产物」。

给课表配六个显示开关，是同一个错误换了个地方：

- **绝大多数工作室不会去调**，默认值就是最终形态。那就把默认值做对。
- 六个布尔 = 64 种组合，**其中大部分我们从来不会看一眼**，而每一种都是
  一个可能崩掉的版式（比如只剩时间没有课名的一行）。
- 每一个开关都是在问工作室一个他们没有立场回答的问题。
  「要不要显示适龄段」——他不知道，他只想让家长看懂。

### 那些字段怎么定

**一条规则代替六个开关：有内容就显示，没内容就不显示。**

没填地点 → 不出现地点那一行，也不出现「地点：」这个空标签。
课程没选 → 显示 `label`。没填适龄段 → 不显示。
**这是自配置的，而且不会产生空标签。**

### 只保留两个开关，各有硬理由

| 开关 | 在哪 | 为什么不能用"有内容就显示"代替 |
|---|---|---|
| 老师是否公开 | **按人**，团队管理里 | 这是**个人信息同意**，不是版式偏好。名字一直有内容，但"有内容"不等于"他同意上公网" |
| 余位是否公开 | 按租户 | 这是**商业判断**：一个班只剩 2 人时，"还有 8 个位置"传达的是冷清不是稀缺 |

### 如果你还是想给控制权

那我建议给**一个**选择，不是六个：**「简洁 / 详细」两档**。

- 简洁：时间 · 课程名 · 余位
- 详细：再加 老师 · 地点 · 适龄段 · 时长

一个决定，而不是六个；两种版式，而不是 64 种。这个我可以做，成本约 1 小时。

**但我仍然推荐先只发默认值。** 等真的有工作室提出要求，再看他要的是不是
这两档——现在加，是在为一个还没出现的需求付版式复杂度。

## 4. 余位用颜色 —— 要做，但有三条改动

方向对，颜色是这里最快的信息通道。三个约束：

### 4.1 颜色不能是唯一信号（WCAG 1.4.1）

芯片里**必须有字**：「还有 3 位」/「快满了」/「已满」。
颜色是第二信号。色盲访客、灰度打印、深色模式下都要读得出来。

这条是硬的——本轮之前刚因为同类问题改过播放键（浅色画上 1.22:1）。

### 4.2 不能是实心填充（Design_Constraints §1.1）

语义色**只允许** `*-soft` 底 + 同色文字 + `*-border` 描边，不做实心块。
一屏最多一个饱和填充，而那一个已经给了「预约体验」按钮。

好消息：这三种芯片的求解已经做完了——`success` / `warning` 在九套主题、
明暗两种模式下都过了彩度下限和对比度。**直接用，不用新配色。**

### 4.3 「满了」建议用中性灰，不用红

这一条我和你的想法不同，说清楚理由，最后你定。

**红（danger）的意思是"出问题了，需要处理"。** 一个满员的班不是故障——
对工作室是成绩，对家长是"我要排候补"。用红色：

- 让一门**卖得最好的课**在页面上看起来像是坏了;
- 也磨损了红色本身——它应该留给"付款失败"这种真的出错的场合。
  一个页面上到处是红色的产品，红色就不再意味着什么。

建议映射：

| 状态 | 芯片 | 文案 |
|---|---|---|
| 有位 | `success-soft` 绿 | 还有 N 位 |
| 快满 | `warning-soft` 琥珀 | 快满了（还有 N 位） |
| **已满** | **中性 `--muted` + 线框** | 已满 · 可加候补 |

灰掉的那一行同时传达了"这一行不再是同一种可点"，这比红色更准确。

### 4.4 阈值要按比例，不能按绝对数

20 人的班剩 3 个 = 15%，是快满了。
4 人的班剩 3 个 = 75%，宽得很。

建议：**快满 = 剩余 ≤ max(1, 容量 × 25%)**，向上取整。
（`--muted` 那档就是剩余 = 0。）

绝对阈值在这个产品里必然出错，因为容量从 1（一对一）到 30（大班）都有。

## 5. 建议的落地顺序

你说的"先完善后台"是对的，而且有一个额外的好处：**后台先跑一段，
数据先长出来，门户那一版就有真实内容可以验收**，不用靠假数据判断版式。

| 版本 | 内容 | 估时 |
|---|---|---|
| **v8.8.0** | 深色变亮 + 后台全部字段（课程/老师/公开/地点/停课/周数）+ 冲突判定改按老师 | ~1.5 天 |
| **v8.9.0** | 公开接口（时区投影）+ 门户课表板块 + 余位芯片 | ~1.5 天 |

拆两版的理由不是工期，是**第一版没有任何对外影响**——后台字段加完，
公网上什么都不会变。可以放心先发、先用。
