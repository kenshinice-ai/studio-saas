# StudioSaaS 使用者视角审阅与可执行优化方案

日期：2026-09-06

代码基线：`50e89df`，`VERSION=10.15.0`

交付性质：审阅、实测证据和优化方案；**未修改产品代码、未部署**。

## 1. 结论与建议顺序

StudioSaaS 已经具备完整的工作室业务骨架。现在最有价值的投入，是让用户在现有功能之间顺利完成工作：选中的课程带进报名、设好的跟进时间不会消失、收款后能直接找到发票、手机上能正常修改官网。

建议按以下顺序推进：

1. **先修复三处实际阻断或误导操作的问题**：手机 Studio Admin 编辑区、跟进日期、发票深链接。
2. **再接顺客户与前台的流程**：选课报名、约课错误恢复、家长查询切换语言、到期跟进队列。
3. **最后调整信息优先级和视觉表达**：工作台首屏、品牌编辑器入口、营销页行动文案、课程查找效率。

不建议启动大规模 CMS 重写、重做主题生成器，或再造一套组件系统。当前的共享组件、主题和业务能力足以承载大部分优化。

本轮没有证据支持全产品 P0。下文将影响重要任务的明确缺陷列为 P1，将效率提升及设计建议列为 P2/P3；优先级同时考虑影响范围、发生条件和是否有替代路径。

## 2. 这次具体看了什么

### 2.1 使用者与任务

| 使用者 | 核心任务 | 实际涉及的产品表面 |
|---|---|---|
| 正在选系统的经营者 | 看懂产品、判断是否适合、了解价格、体验演示 | 产品首页、定价信息、演示入口 |
| 首次来访的家长或学员 | 了解课程和时间、提交咨询、知道下一步 | 租户门户、报名、公开课表、作品页 |
| 已有学员或家长 | 查询课时、下次上课、作品和记录 | 学员专区 |
| 前台 | 找到今天要联系的人、处理报名、建档、排课、收款 | CMS 工作台、待处理、学员、课程、账单与充值 |
| 教师 | 快速找到当天名单、签到、查看学员、上传作品 | CMS 手机工作台、课程安排、学员与作品 |
| 工作室负责人 | 了解经营、调整官网、预览和发布 | CMS、Studio Admin |

Super Admin、独立部署版、真实支付/Xero 外部操作不属于本轮深度体验范围。安全问题不展开；仅保留实现优化时必须遵守的现有产品边界。

### 2.2 方法和证据分级

- **[实测]**：用当前代码启动本地 Flask 服务与独立临时 PostgreSQL，使用项目自带的美术、音乐虚构演示数据，通过真实 Chrome 操作得到。
- **[源码确认]**：追到当前活动源码和调用链；未必执行了该链路所有操作。
- **[模拟验证]**：在浏览器中模拟错误响应或临时覆盖 CSS，验证特定界面行为；不等于生产环境发生过该故障。
- **[设计建议]**：基于当前界面的专业判断，需要原型或真实使用者任务测试验证收益。

首轮保存了 **19 个页面状态**，随后补充表单、查询、跟进、发票、不同角色和响应式诊断。记录位于 [实测证据目录](ux-review-2026-09-06/observations.json)、[交互记录](ux-review-2026-09-06/interactions.json)、[关键问题复现](ux-review-2026-09-06/final-probes.json)。截图均为虚构数据。临时演示服务和数据库已在交付前关闭。

实际尺寸包括 375px 手机、1440px 桌面；Studio Admin 额外检查 768px、1024px。CMS 截图主要记录内部滚动容器的当前视口，不能从截图高度推断整页内容高度。公开页面的整页截图也不代表每张延迟加载图片都已滚动触发，因此没有把截图中的空图片区域直接认定为产品缺陷。

主题覆盖需要准确理解：美术为 `atelier-clay` 明亮主题，音乐为 `recital-plum` 明亮主题。音乐页面即使浏览器偏好设为 dark，实际 `data-brand-scheme` 仍是 light，这是租户固定明亮配置的正确行为。证据中含 `dark` 的早期截图文件名表示浏览器请求偏好，**不构成租户暗色主题通过的证据**。本轮未跑完整 15 种主题模式矩阵。

### 2.3 活动实现与文档差异

当前 CMS 源码虽然位于 `legacy-root/src/`，却是活动实现；浏览器加载 `backend/frontend/assets/cms-app.js`。公开租户页面由 `tenant-template/` 生成，Studio Admin 活动文件是 `backend/frontend/studio-admin.html` 及其 JS。

`docs/README.md`、`Product_Surface_Model.md` 部分版本说明仍停在 v10.13.0；9 月 3 日的 CMS 改善记录和实际代码已经包含后续优化。本报告以当前代码和本地实测为准，不沿用旧文档的“尚未实施”结论。同目录其他审阅稿保持原样，本文件提供独立的本地运行证据。

## 3. 应当保留的已有成果

- **产品分工清楚**：CMS 管日常运营，Studio Admin 管官网与品牌。两者有互相到达的入口，无须合并成一个巨大后台。
- **报名已经做了减负**：基础信息优先、选填折叠；快速报名空提交会聚焦名字并标记错误，切换英文后本次输入的姓名和手机号保留。
- **课程安排已经做过优化**：周日期条、整月展开、今日签到/排课设置分区、派生未签到状态、当日操作菜单都存在。
- **CMS 有可复用基础**：`Tabs`、`TabPanel`、`FilterBar`、确认对话框、空状态、全局搜索和浏览器前进后退机制，不应重复建设。
- **账单功能并不空缺**：家庭账户、发票、收款、退款、结算、导出及学员档案到家庭账单的链接已经存在。
- **发布流程已有状态保护**：保存草稿、发布、变更分组、历史版本、未保存提示和离开提醒已经存在。后续应提升可理解性，而非重新设计发布机制。
- **品牌差异已有体现**：美术和音乐的文案、图片、配色、课程信息有明显区别；不建议为了统一后台而抹平租户门户的性格。

## 5. P1：先处理会打断任务的具体问题

### P1-01 · 手机 Studio Admin 的编辑区实际只有约 2px

**场景**：负责人在 375px 手机上进入品牌基础，准备改名称或联系方式。

**证据**：`.settings-shell` 宽 343px，实际计算列宽为 `1.98438px 320px`，`.settings-panel` 约 2px，预览区占 320px。页面总高约 8050px，却没有整页横向溢出。截图中的字被压成窄条，编辑区与预览互相干扰。

**根因**：`backend/frontend/studio-admin.html:2073` 的手机单列规则，被后面的 `:2156` 无条件双列规则覆盖；末尾手机规则仅再次恢复外层 `.workbench-layout`，没有恢复内层 `.settings-shell`。在浏览器末尾临时添加手机单列规则后，编辑区从 2px 恢复到 343px。这个诊断只改变浏览器内存，产品文件未修改。

**方案**：修正这一个页面的 CSS 顺序/作用域。手机上编辑器占满可用宽度；预览放在编辑之后或显式“查看预览”模式。先恢复布局，再决定是否收起预览。无需改黄金比例 token 或生成器。

**验收**：375/768/1024/1440px 下逐个进入品牌、报名表、公开课表和发布页；名字、电话、下拉和上传按钮可用；固定保存栏不遮挡最后一个字段；检查编辑区、预览区和控件宽度，不能只检查 `scrollWidth`。

### P1-02 · 更新联系状态会无意清除已有跟进时间

**场景**：前台昨天设好了下次联系时间，今天刷新页面，点一次“已联系”。

**实测过程**：给虚构报名设置 2026-09-10 09:00（墨尔本时区）；重新打开待处理，日期框为空；点击“已联系”，请求发送 `nextFollowUpAt: ""`；服务端原日期变成 `null`。这是当前实现中真实发生的数据变化，不只是显示问题。

**根因**：`cms-app.jsx:305` 的 `followUpDates` 初值为空对象；`students.jsx:409` 只读取这个临时对象；`cms-app.jsx:3134` 再把空值作为显式清除发送。服务端本已支持“字段未提供则保持原值”，见 `api_v1/students.py:663`。

**方案**：显示服务端保存的日期；区分“未改日期”“改了日期”“明确清除”三种状态。只改联系状态时不发送日期字段，清除需有清晰动作。所有转换按现有工作室时区处理。

**验收**：设置 → 刷新 → 改状态后日期不变；改日期后保存正确；显式清除才变空；今日到期提醒仍能找到该报名；中文与英文日期含义一致。

### P1-03 · “查看发票”落到了错误的账户筛选结果

**场景**：完成结算后点“查看发票”，或从学员记录进入原发票。

**证据**：`cms-app.jsx:2582`、`:2674` 以及 `student_profile.jsx:128` 把发票 ID 放进 `recordId`；但 `cms-app.jsx:3832` 将其一律传为 `BillingPanel.accountId`，面板使用 `?accountId=` 查询。

本地使用真实存在的虚构发票 `INV-0004` 访问相同深链接，出现“只看这个账单账户”“0 张”“还没有发票”。按它的真实账户 ID 查询则返回 1 张。复现了链接落点；本轮未重新执行一笔完整结算。

**方案**：路由显式区分 `accountId` 与 `invoiceId`，分别负责筛选列表和打开详情。对历史 `?view=billing&id=` 保留明确的兼容解析，不靠碰运气猜 ID。不能修好发票链接却破坏现有的学员 → 家庭账户链接。

**验收**：结算 → 查看新发票、退款 → 查看原发票、学员 → 家庭账单、直接刷新目标链接、前进/后退均正确；目标发票不存在时显示“找不到该发票”，不能伪装成“从未开票”。

### P1-04 · 点了某门课程报名，表单却不知道选的是哪门

**场景**：家长看完“钢琴一对一”后点报名，期待下一页已经知道自己的意向。

**证据**：`tenant-template/index.html:1893` 附近所有课程 CTA 只使用 `#join`；本地点击首个课程报名后，URL、表单标题、字段值都未携带选中的课程。共享提交函数也没有由该入口传入的课程上下文。

**方案**：报名顶部显示“你正在咨询：课程名”，允许更换/清除。第一版复用当前表单与提交接口，把用户确认的意向写入现有可见咨询内容；跨页面快速报名可带课程标识并在当前租户内解析。若以后需要精确课程转化统计，再设计结构化字段，不应本轮直接改公共 API 合同。

**验收**：美术和音乐均能带入正确课程；切换语言、返回浏览后仍保留；未选课程时维持通用咨询；已下架课程提供重新选择；CMS 前台能看见同一意向。不把咨询意向表述为已获得席位。

### P1-05 · 公开约课的错误体验弱于现有快速报名

**实测**：在音乐课表打开预约，空提交后焦点停在 `bookSubmit`，没有 `aria-invalid` 字段标记，只有顶部“请填写姓名与手机号”。对照快速报名，已有首个错误聚焦和字段错误。

**模拟验证**：返回 `{error:"validation_error", message:"Please check the mobile number."}` 时，界面直接显示 `validation_error`。源码 `tenant-template/timetable.html:417` 优先取机器码 `data.error`。

**方案**：复用现有报名的字段级反馈约定：标明具体字段，错误摘要和字段关联，聚焦首个错误；优先展示可读 `message`，没有时用当前语言的恢复提示。请求期间显示“发送中”，失败保留输入。成功态保留已经做对的“等待工作室确认”和候补说明。

**验收**：姓名缺失、电话缺失、服务端校验失败、网络中断、重复请求、正常受理均给出清晰下一步；Escape 退出后回到触发按钮；读屏能感知错误和成功反馈。

错误提示的设计依据可参考 [W3C 表单通知指南](https://www.w3.org/WAI/tutorials/forms/notifications/)，对话框键盘行为参考 [WAI-ARIA Dialog Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)。

### P1-06 · 家长切换语言会丢失当前查询结果视图

**实测**：虚构家长用姓名、手机和演示访问码成功查询后切换英文，结果从可见变为隐藏，需要再点查询。姓名和访问码仍在，**不是凭据被清空，也不是本轮证明了会话失效**。

**根因**：`tenant-template/index.html:1173` 在语言变化时调用 `resetMyView()`；该函数恢复查询表单、隐藏结果，没有重绘现有结果。

**方案**：保留当前有效会话和已查询数据，按新语言重绘金额、日期及固定标签。重新请求失败时保留可理解的状态，不静默跳回入口；不把访问码转成持久保存。

**验收**：zh → en → zh 后仍是同一学员、同一课时与记录；作品可继续查看；显式退出保持现有退出行为；真正会话过期时再提示查询，而非把语言切换当成退出操作。

## 6. P2：让日常工作更快、更容易理解

### P2-01 · 待处理从“很多完整卡片”变成“今天要做的队列”

当前已经有新报名/约课/成长报告分区及联系状态，不需要从零做 CRM。缺口在任务筛选与信息密度：新报名逐条完整展开，没有本地姓名/电话搜索、状态筛选和到期优先视图；工作台“报名跟进到期 → 处理”只进入整个待处理页面。375px 首屏基本容纳一张申请。

**建议**：保留业务类型分区，在新报名内复用 `FilterBar`，加入“今天需跟进 / 未联系 / 已约试听 / 全部”和搜索。默认显示姓名、意向、状态、下次联系时间与一个主要动作；留言、初始课时、拒绝原因等按操作展开。工作台到期入口携带筛选条件，处理完成留在队列当前位置。

第一版使用现有状态和日期，不必同时引入销售看板、自动短信或新的任务系统。建议原型如下：

```text
待处理   新报名 4｜约课 3｜成长报告
[今天需跟进] [未联系] [已约试听] [全部]    搜索姓名 / 电话
Isla Moore · 想约周三晚课 · 今天到期       [记录联系] [详情]
Finn Davis · 初次体验     · 尚未联系       [记录联系] [详情]
```

**验收**：准备 30 条虚构申请，前台能在 30 秒内找到两条今天到期的记录；处理后无需重新搜索或滚回顶部；空筛选结果明确提供“清除筛选”。计数区分报名与约课，不重复计算获客。

### P2-02 · 工作台首屏少重复入口，多显示待完成任务

9 月 3 日已经合并过提醒，不能再次按旧报告要求重做。当前手机 owner 首屏仍先出现“今日重点”四入口、“今日指挥台”四入口及统计卡；待处理、今日课表和充值入口有重复。

**建议**：在现有布局上选出每个角色的一组主动作。前台优先到期跟进/到课，教师优先最近一节课和未签到人数，owner 优先异常摘要和经营入口。已有的学员专区下移、经营真账折叠决定保持不变。先做低保真对比，确认删除的是重复入口而非任务能力。

**验收**：教师在 375px 手机上从首页到当天名单不超过 2 次点击；前台进入到期队列不超过 2 次；同一任务的相同计数在主内容首屏不重复出现。签到的现有课程、日期、扣课时语义保持明确。

### P2-03 · 品牌编辑从“重新选系统”转向“修改当前官网”

当前品牌基础首先完整展示 8 个行业选择和主题卡片，名称、联系方式等靠后。这个顺序适合首次配置，对已营业工作室修改一个电话则过长。手机顶部 12 个工作区入口还占据大块首屏。

**建议**：已配置租户先显示“当前行业 + 当前主题”摘要及“更换”入口，将工作室资料前置；首访保留现有三步引导。手机导航改为当前分区按钮加可展开分组列表。预览保留，但明确提供“编辑 / 预览”，避免把完整预览始终堆在编辑任务中。

保存栏清楚区分“未保存”“草稿已保存、尚未发布”“已发布版本”。发布变更摘要在现有分组上补充变更字段和跳转，例如“联系电话变更 → 查看”，无需另造发布流程。

**验收**：已配置 owner 在手机上找到并修改联系电话、预览草稿，90 秒内完成且知道公众页面尚未改变；更换行业仍是明确动作；发布/还原沿用现有契约。

### P2-04 · 英文使用者首次进入后台时不应先猜语言开关

**实测**：全新 `en-AU` 浏览器进入 Studio Admin，标题仍为“工作室管理员登录”。`i18n-runtime.js:45` 的逻辑只有“已保存英文”或“默认中文”，没有浏览器语言回退。CMS 与两个控制台共享该机制，后两者的首访场景需要补测。

**建议**：明确语言优先级：已保存的用户选择 → 支持的浏览器语言 → 项目默认语言。如果要支持分享语言链接，再单独约定 URL 参数优先级。切换后台语言不改租户公开语言和正在编辑的双语内容。

**验收**：全新 en-AU、zh-CN 浏览器分别可直接理解登录页；已有偏好不会被重置；内容字段中的中文、英文原文不被改写。

### P2-05 · 让“没加载到”和“确实没有”可区分，并保护正在填写的内容

**源码确认**：充值页面获取付款账户和税码失败时返回空数组（`cms-app.jsx:430`）；学员关联账单读取失败也归为空数组并隐藏区块（`student_reports.jsx:225` 起）。这些路径可能让前台误以为尚无账户或记录。并非所有页面都这样，账单主面板已经有显式错误状态。

**建议**：将高频任务统一为加载中、成功空状态、失败可重试、提交中和已成功五类。关键关联数据失败时在原位显示重试，不引导重复建档。对新建学员、充值、上传说明等长输入，补做“页面刷新、后台切换、会话失效”任务测试，再给确认存在丢失风险的表单加内存级草稿/离开提醒。

不要默认把所有客户和交易输入长期写入浏览器存储；也不要在恢复会话后自动重复提交收款或签到。状态恢复与执行操作应分开。

**验收**：模拟账户接口 500 后显示加载失败，恢复后重试成功且输入保留；刷新/离开行为可预期；网络故障后不会误报成功或重复执行。当前这部分是源码问题和验证计划，不是本轮跑通了全部故障场景。

### P2-06 · 公开课表让家长按自己的空闲时间找课

现有日期分组、名额、候补、停课说明和工作室时区值得保留。课程多、展示周期长时，连续日期列表需要逐屏查找，缺少轻量的课程/老师/日期筛选。

**建议**：先增加“本周 / 下周”、课程类型和只看可申请课程；具体过滤项只在数据足够时出现。选择后保留筛选条件，并把完整的课程日期、时间、地点带入预约弹窗和成功摘要。不要一开始就上复杂的拖拽周历。

**验收**：用四周、多位老师的虚构课表，让家长找到“下周三晚上的钢琴课”；筛选无结果时有重置入口；已满课程在用户主动筛选之外仍可明确作为候补找到；申请成功始终不等于确认席位。

### P2-07 · 营销页把品牌叙事变成可预期的入口

首页的空间叙事、艺术气质与行业示例有辨识度，不建议改成普通后台软件模板。可优化的是入口含义：首屏“走进这个系统”实际跳往页面介绍区；“四个相连界面”需要读者先理解内部模块。

此外，`product-home.html:146` 附近将“海报 → Canvas → WebGL”显示给访客。它解释实现过程，无法帮助经营者判断是否适用；设置 `aria-hidden` 也不会使视觉内容消失。

**建议**：主入口使用与落点一致的“看一次日常工作演示”，次入口“预约演示”；若仍只滚动介绍区，应写“了解如何运作”。模块先说任务，再用小字标注产品名：接住咨询、安排课程、完成签到与收款、更新官网。技术渲染标签删除或仅用于开发调试。已存在定价和演示链接，无需再建设一套销售入口。

**验收**：给首次接触的经营者 30 秒看首屏，能说出服务对象、解决的主要工作、点击两个按钮分别会发生什么。真实客户证明和产品边界保持准确。

## 7. P3：视觉和文案的最后一轮整理

**P3-01：以任务语言统一高频操作。** 当前不同入口存在“充值与退款”“充值结算”“快速充值”等措辞。先映射到实际能力，再统一主标题与动作副词；不把发票、付款、充值课时等不同业务概念全部改叫“支付”。借助现有术语字典和双语检查，避免仅改中文造成英文孤儿键。

视觉上优先优化联系人、金额、课程日期、待处理状态的层级。次要技术状态与长解释退居辅助位置；成功/危险色继续表达真实状态，不用于装饰模块。保留租户主题、当前 CJK 字体和语言专用排版，不提出未经测量的“全站对比度不达标”或全站字号重置。
