# v10.0.0 → v10.2.2 复盘：这一轮教了我们什么

> 2026-08-14。26 个提交，其中 3 个是修我自己在同一轮里写进去的 bug。
> 这份文档只做诊断和方案，不改代码。

一天之内从 v10.0.0 发到 v10.2.2，中间连打两个补丁版本。这不是节奏问题——
两个补丁修的是同一类错误，而那类错误在这一轮里其实出现了**七次**，只是前
五次被守卫接住了，后两次没有。

值得记下来的不是「要更小心」，而是：**哪些错误这套体系接得住，哪些接不住，
以及为什么。**

---

## 一、接得住的：两份手写清单

这一轮里，同一个形状的 bug 出现了七次：

| # | 两份清单 | 后果 | 怎么发现的 |
|---|---|---|---|
| 1 | 归档清单 vs 真实的租户表 | 归档静默丢掉 3 张表，含家长姓名与电话 | 改成从 SQL 推导，第一次跑就抓到 |
| 2 | `IMPORT_ORDER` vs `SNAPSHOT_TABLES` | Edition 导入器每次都 `SystemExit` | 加了对比测试 |
| 3 | 侧栏标签 vs 页面标题 | 同一页在两处叫两个名字 | 用户看截图发现 |
| 4 | `RATE_BASES` vs 面板的中文名 | `per_hour` 印在老师工资单上 | 用户看截图发现 |
| 5 | 手册标签表 vs 实际导航 | 文档描述的是已经改过的产品 | 既有守卫抓到 |
| 6 | i18n 字典 vs 实际渲染的字符串 | 英文界面里成片的中文 | 用户看截图发现 |
| 7 | 归档清单 vs 新增的 `tenant_billing_identity` | 同 #1 | 修好的守卫当场抓到 |

**#1、#2、#5、#7 被守卫接住了，#3、#4、#6 是你看截图发现的。**

差别很清楚：被接住的那些，守卫是**推导式**的——从 SQL、从目录、从另一份数据
结构里算出应该有什么，再和实际的比。没被接住的那些，两份清单都是人手写的，
没有任何东西知道它们本该相等。

### 方案 A：把剩下的手写清单也推导化

现在仍然是手写、且有配对物的：

| 清单 | 它应该等于什么 | 现在靠什么保证 |
|---|---|---|
| `RATE_BASES`（Python） | 数据库 CHECK 里的枚举 | 无 |
| `scheduling` 的 `kind` 常量 | `lesson_exceptions.kind` 的 CHECK | 无 |
| `engagement` / `status` / `kind` 等 | 各自的 CHECK 约束（全库共 50 处枚举 CHECK） | 无 |
| `BASELINE_FEATURES` / `ADDON_FEATURES` | `plans.features` 里实际出现的键 | 无（v10.0.0 就是这里漏的） |
| `test_manual.py` 的 `SECTIONS` | `manual.html` 里的 `<section id>` | 有（顺序比对） |
| `SHOTS` | 手册里引用的图片 | 有（manifest 比对） |

**具体做法**：写一个 `test_sql_enums_match_python.py`，从 `backend/db/migrations/*.sql`
里正则出所有 `CHECK (x IN (...))`，和 Python 里同名常量比对。这不是新发明——
`test_health.py` 已经在用同样的手法解析 `CREATE TABLE`。

代价：一个测试文件，约 60 行。收益：全库 50 处枚举 CHECK 中，凡在 Python 里
有对应常量的，从此不可能单边修改。

注意这里要**只比对有配对物的那些**，不是要求 50 处都有 Python 常量——
大多数枚举只在 SQL 里用，那没问题。会出事的是「两边都有、但只改了一边」。

### 方案 B：给「人读的字符串」一条渲染级守卫

i18n 那次（#6）特别值得说，因为我第一次尝试用正则扫源码，扫出 238 条
「文案」，大半是代码。真正管用的办法是**把界面切到英文，遍历文本节点，
找出还是中文的**——量渲染结果，不量代码。

那次是手工做的。可以固化：一个 Playwright 脚本，登录演示租户，把每个页面
在英文模式下走一遍，收集残留中文，输出成清单。**不必让它失败**——作为
`verify_local.sh` 的一个报告项即可，因为「哪些字符串该翻译」有判断成分
（人名、品牌名不该翻）。

代价：一个脚本 + verify_local.sh 里一行。收益：这类问题从「用户截图告诉我」
变成「发布前自己知道」。

## 二、接不住的：测试测的是源码，不是行为

这是这一轮最重要的发现，也是最难看的一条。

```
67 个测试文件，2564 条用例
其中连真数据库的：1 个文件，17 条
其中对 v10 钱这一层发过 HTTP 请求的：0 条
```

`test_tenant_isolation.py` 有 225 处检查、跑真库、用 `app.test_client()`
发真请求——**但它覆盖的是 v10 之前的路由面**：学员、课程、排课、作品、报名。

钱这一层的约 50 条路由（billing / payments / teaching / scheduling /
progress-reports / xero / reports）在任何测试里都**没有被请求过一次**。

### 这直接解释了这一轮上线后才发现的三个 bug

| bug | 为什么静态测试看不见 |
|---|---|
| `assemble()` 把 `date` 塞进 `json.dumps` → 500 | 需要真库**且**学员有课堂笔记 |
| 有已开具发票的租户删不掉 | 需要真库**且**租户开过发票 |
| `plans.features` 缺三个键 | standalone 全开、测试直接授权，两条路都绕过了套餐表 |

三个都有同一个特征：**测试夹具比真实租户简单**。空租户序列化得好好的，
没开过票的租户删得掉，全开的实例不查套餐。**坑恰好埋在用得最多的租户里。**

### 方案 C（最高优先级）：把钱这一层接进隔离套件

harness 已经存在——`server.app.test_client()`、CSRF 客户端类、真库夹具，
全都在 `backend/test_tenant_isolation.py` 里现成。缺的只是把新路由加进去。

最低限度要覆盖的三件事，每条路由：

1. **跨租户拒绝**。A 租户的令牌读不到 B 租户的发票、收款、课酬、报告。
   这是多租户 SaaS 的生存线，而现在最敏感的那批数据（谁欠钱、谁拿多少钱）
   完全没验过。
2. **返回 2xx 而不是 500**。用一个**有数据的**租户，不是空租户。
3. **权限拒绝**。老师读不到 `payroll:read`，前台开不了退款。
   `auth.py` 的静态测试已经断言了权限表，但没验过路由真的在用它。

**关键设计**：夹具必须是「一个真实工作室会有的样子」——有学员、有课堂笔记、
有已开具发票、有收款、有课酬期间。可以直接复用 `_seed_money_layer()`：
它已经写好了，v10.1.1 起就是演示租户的基线。**让测试夹具和演示数据是同一份
东西**，这样它们不会分头腐烂，而且演示数据本身也就被测试覆盖了。

代价：约 300 行测试。收益：这一轮三个线上 bug 中的两个会在发布前失败。

### 方案 D：给「有数据的租户」一个共享夹具

比方案 C 更根本的一条：现在每个测试各自造夹具，于是每个夹具都造得刚好够用，
也就刚好比真实租户简单。

建议做一个 `conftest.py` 级别的 `populated_tenant` 夹具，内容就是
`_seed_money_layer()` 那一套。任何测试要「一个真实的租户」时用它，而不是
自己 `INSERT` 两行。

这会让「夹具太干净」这类 bug 系统性变难。

## 三、DOM 查询查不出版面

v10.2.0 和 v10.2.1 是同一个 bug 犯了两次：设置块从 `fixed` 覆盖层变成正常流，
但它在 DOM 树里的位置没跟着改。

两次发布我都验证了：面板数量、可见数量、`aria-selected`、URL 往返、后退键——
**全绿**。元素是对的，位置是错的。

### 这不是「不够仔细」，是验证方式选错了层

DOM 查询回答的是「元素存不存在、属性对不对」。版面回答的是「它画在哪儿」。
第二个问题只有两种办法能答：**看截图**，或者**量坐标**。

第三次我两样都做了（1440px 与 375px 截图 + `getBoundingClientRect`），当场就对了。

### 方案 E：改动布局时的验证清单

不需要新工具，需要一条写下来的规矩，进 AGENTS.md：

> 当改动**决定东西画在哪儿**的代码（定位方式、DOM 中的位置、grid/flex 结构、
> 断点），DOM 查询不算验证。必须至少做到其一：
> - 在桌面与手机两个宽度截图并看；
> - 量 `getBoundingClientRect()` 的坐标并断言相对关系。

这一轮我为此连发两个补丁版本，本可以在 v10.2.0 就看一眼避免掉。

### 方案 F：几条结构性断言（便宜，值得）

版面整体没法静态测，但**顺序关系**可以，而且正好是这两个 bug 的形状：

- 页脚必须是 `<main>` 里的最后一个元素（已加）
- 设置块必须在 `<main>` 之内（已加）
- 没有面板可以内联写 φ 网格而不带断点（已加）

这三条不能防住所有版面 bug，只能防住**已经发生过的那三种**。这仍然值得——
回归防护的价值就在于此。

| 项 | 状态 | 备注 |

| 周期账单自动生成草稿 | 未做 | 账单页空状态里承诺了这件事，但它还不存在 |

最后一条要单独说：**账单页的空状态写着「周期账单会自动生成草稿」，而这个功能
不存在**（已核实：`backend/studiosaas/` 里没有任何周期账单的实现）。 这是文案在替一个未实现的功能背书。要么把功能做了，要么改文案——
现在这样，第一个认真读它的工作室会等一个永远不来的草稿。

## 五、建议的优先级

按「防住的损失 ÷ 花的力气」排：

1. **方案 C**：钱这一层接进隔离套件（跨租户 + 有数据 + 权限）。
   *这是唯一一条防的是「客户看到别人家的钱」的。*
2. **方案 D**：共享的 `populated_tenant` 夹具，复用演示数据种子。
   *让方案 C 不至于又造出一个太干净的夹具。*
3. **方案 E**：AGENTS.md 里那条布局验证规矩。
   *零成本，直接防住这一轮两个补丁版本。*
4. **方案 A**：SQL 枚举 vs Python 常量的推导式守卫。
   *全库 50 处枚举 CHECK，其中一处已经漏到工资单上了。*
5. 改掉账单空状态里那句不成立的承诺。
6. **方案 B**：渲染级 i18n 报告。
7. `<FilterBar>` 接入其余四页。
8. 拆 `api_v1.py`（比拆前端更急，但也更需要一整块时间）。

前三条加起来大概是一天的工作量，而它们对应的是这一轮**三个线上 bug 中的三个**。

## 六、这一轮做对的事（值得保留的）

复盘不该只列问题。

- **发布账本**（`test_release_ledger.py`）每一次版本推进都拦住了漏改的地方，
  一次没漏。README 三行分别填、填在事情真的发生之后，也确实防住了「版本号
  暗示了一个还没发生的部署」。
- **数据库层面的不变量**——发票不可改、号码不跳号、分配不超额、Xero 闸门是
  CHECK 约束——全部在真库上验过，而且**每一条都在这一轮真的拦住过东西**，
  包括拦住我自己（重置脚本第一次跑就被不变性触发器拒绝，那是它对）。
- **HANDOFF 纪律**。每次改动当场更新，所以上下文压缩之后没有丢过线索。
- **「先修错的，再加新的」**的顺序。`role="tablist"` 那个不成立的声明和
  `per_hour` 那个漏出的枚举，都是先修掉才动新功能。

## 附：一条贯穿全篇的话

这一轮所有被接住的 bug，靠的都是**从事实推导出来的守卫**——问 SQL、问目录、
问渲染出来的页面。所有没被接住的，靠的都是**两份人写的清单碰巧一致**。

区别不在于聪明，在于**有没有一个不会说谎的来源**。

数据库知道有哪些表，目录知道有哪些文件，浏览器知道东西画在哪儿。
只要还有东西是从它们那里问来的，它就不会悄悄错。
