# 隔离、稳定与工作流：一套更小的方案

> 2026-08-15。只做方案，不改代码。
> 这份取代 [Retrospective_2026-08-14.md](Retrospective_2026-08-14.md) 第五节的优先级。

---

## 〇、先承认上一版方案错在哪

昨天我提议：给钱这一层每条路由加「跨租户 + 权限 + 有数据」三类测试，约 300 行。

那是**在测试一个约定**。约定之所以需要 N 条测试，是因为每条路由都是一次
「忘记写 `WHERE tenant_id`」的机会。加到 50 条，第 51 条路由照样可以忘。

「只做必须的检查」这句话的正确读法不是「少测一点」，而是：

> **让不必检查的事情，在结构上不可能发生。**

下面整套方案就是照这个改写的。结论是测试要**减少**，不是增加。

## 一、最要紧的一件事，和隔离无关

生产查到的事实：

```
应用连库角色 = studiosaas
  ├─ 拥有 public 下全部 78 张表
  └─ rolsuper = true      ← 超级用户
```

**这个 Web 应用是以数据库超级用户的身份在跑的。**

后果按严重程度：

1. 任何一处 SQL 注入不是「读到别人的数据」，是**整库沦陷**，包括 `DROP DATABASE`。
2. 应用代码里任何一个拼错的 `DELETE` 没有任何东西拦得住——没有权限边界。
3. **超级用户无条件绕过 RLS。** 所以下面第二节的方案，不先做这一条就等于没做。

### 方案 1：给应用一个受限角色（最高优先级，与其他方案独立）

```sql
-- 迁移的属主：保留 studiosaas（它要能 CREATE TABLE / ALTER）
-- 应用运行时：一个既不是属主、也不是超级用户的角色
CREATE ROLE studiosaas_app LOGIN PASSWORD '...';
GRANT CONNECT ON DATABASE studiosaas TO studiosaas_app;
GRANT USAGE ON SCHEMA public TO studiosaas_app;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO studiosaas_app;
-- 明确不给：CREATE、DROP、TRUNCATE、ALTER
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO studiosaas_app;
```

应用的 `STUDIOSAAS_DATABASE_URL` 换成这个角色；`entrypoint.sh` 跑迁移时仍用
`studiosaas`。两个角色，两件事，互不干扰。

**代价**：一条迁移 + 一个环境变量 + entrypoint 分开两个连接串。约半天。
**收益**：注入的爆炸半径从「整个数据库」缩到「这一个租户能看到的行」——
而且这是 RLS 生效的前提。

**注意**：`TRUNCATE` 不给很重要。租户彻底删除走的是 `DELETE FROM tenants`
级联，那条路照常工作。

## 二、数据库隔离：从「靠纪律」到「靠构造」

### 现状是什么

```
78 张表，73 张带 tenant_id，0 张启用 RLS
173 条路由，169 处 connect()，其中 120 处解析租户
213 段 SQL，180 段写了 tenant_id 过滤
```

剩下 33 段没写的，逐条看过，**全部是合理的**——它们查的是
`users` / `tenants` / `plans` 这类本来就不是租户级的表。

所以：**今天没有已知泄漏。纪律守得住。**

问题不在今天，在于**没有任何东西阻止第 174 条路由忘记**。而这个产品刚刚在
一轮里新增了 50 条路由，全部触碰钱。

### 方案 2：对 73 张表启用 RLS

一次性迁移，形状是统一的：

```sql
ALTER TABLE invoices ENABLE ROW LEVEL SECURITY;
ALTER TABLE invoices FORCE ROW LEVEL SECURITY;   -- 属主也要受约束
CREATE POLICY tenant_isolation ON invoices
  USING (tenant_id = current_setting('studiosaas.tenant_id', true)::uuid);
```

`FORCE` 这一行是大多数 RLS 部署静默失效的地方：**默认情况下表属主不受
自己表上的策略约束**。加上第一节换成非属主角色，两道都堵上。

会话变量在**一个地方**设置——`_tenant_context(conn)`，120 条路由已经都在调它：

```python
def _tenant_context(conn):
    tenant = resolve_tenant(conn, *slug_from_request(request, load_config()))
    with conn.cursor() as cur:
        # SET LOCAL：随事务结束而失效。这里没有连接池，所以本来也不会串味，
        # 但用 LOCAL 意味着「将来加了池子也不会」。
        cur.execute("SET LOCAL studiosaas.tenant_id = %s", (tenant.tenant_id,))
    return tenant
```

`current_setting(..., true)` 的第二个参数是关键：变量没设时返回 NULL 而不是
报错，于是策略变成 `tenant_id = NULL` → 假 → **一行都读不到**。
**忘记设租户的后果是看不见任何数据，不是看见所有数据。** 这是安全的失败方向。

### 这为什么让「只做必须的检查」成立

有了 RLS，昨天那 50 条路由测试全部不必要，替换成 **3 条结构测试**：

```python
def test_every_tenant_scoped_table_has_rls_forced():
    """从 information_schema 推导，不是手写清单 —— 新表自动进入检查。"""

def test_the_app_role_is_neither_owner_nor_superuser():
    """RLS 对属主和超级用户不生效。这条不过，上面那条就是装饰。"""

def test_a_query_without_a_tenant_filter_returns_nothing():
    """把租户变量设成 A，直接 SELECT * FROM invoices（故意不写 WHERE），
       断言查不到 B 的行。这一条验的是「忘记会怎样」。"""
```

第三条是整套方案的证明：它模拟的正是**将来那个会忘记的开发者**。

50 条变 3 条，而且防护范围从「今天这 50 条路由」扩大到「以后所有路由」。

### 这不是从文档里抄的，是在本地真库上跑过的

方案写完后我把它当场试了一遍，两次：

**第一次以超级用户身份**（也就是生产现在的身份）——建表、开 RLS、加 `FORCE`、
建策略，然后查询：

```
① 变量未设时： 2 行     ← 期望 0
② 设为租户 A： 2 行，还能读到 B 的数据
③ 当前角色 rolsuper： true
```

**策略完整存在，完全不生效。** 这就是「不换角色就开 RLS 等于什么都没做」的
现场证据——如果直接上生产，看到的会一模一样：迁移成功、策略在库里、隔离为零。

**第二次以受限角色身份**（非属主、非超级用户）：

```
① 变量未设时：            0 行        ← fail-closed 成立
② 设为租户 A：            只见 A 的数据
③ 明确 WHERE tenant_id = B： （空）
```

③ 是最有力的一条：**一条故意去问别的租户数据的查询，拿到的是空。**
不是「忘记会被接住」，是「问也问不到」。

### 安全的实施顺序（不要一次切换）

RLS 切错了是全站看不到数据，所以分四步，每步可独立回滚：

| 步 | 动作 | 风险 |
|---|---|---|
| 1 | 建 `studiosaas_app` 角色，但**先不用**；测试环境先切 | 零 |
| 2 | 在**测试库**上开 RLS，跑全套测试 | 零（不碰生产） |
| 3 | 生产开 RLS，但应用**仍以属主连接**（`FORCE` 暂不加） | 零——策略存在但不生效，可观察 |
| 4 | 应用切到 `studiosaas_app` + 加 `FORCE` | 真正生效；一条环境变量即可回滚 |

第 3 步是关键的观察窗：策略已经在库里，可以用 `studiosaas_app` 手工连上去
跑真实查询，确认没有东西被误伤，再切。

## 三、只隔离必须的数据

**不加 RLS 的 5 张表，以及为什么**：

| 表 | 为什么不隔离 |
|---|---|
| `plans` | 平台目录。所有租户读同一份，本来就该共享 |
| `schema_migrations` | 迁移账本。属于数据库，不属于任何租户 |
| `tenants` | 租户注册表本身。按 id 查；给它加租户策略是循环定义 |
| `users` | **刻意全局**。一个老师可以在两家工作室教课，他是同一个人、同一个密码。租户归属在 `memberships` 里，那张表有 `tenant_id` 且会被隔离 |
| `cms_notification_reads` | **需要决定**，见下 |

### `cms_notification_reads` 是唯一需要拍板的一张

它是 `(notification_id, user_id, read_at)`，没有 `tenant_id`。租户范围通过
`notification_id` 间接成立。两个选项：

- **A：加 `tenant_id` 列**，和其他表一样加策略。多一列冗余，但规则统一。
- **B：写一条基于 FK 的策略**，`EXISTS (SELECT 1 FROM cms_notifications n
  WHERE n.id = notification_id AND n.tenant_id = current_setting(...))`。
  不加列，但每次读都多一次子查询，而且它是这套规则里唯一的例外。

**建议 A**。这套方案的价值来自「73 张表规则完全一致」，用一列冗余换掉一个
例外是划算的——例外正是将来会被忘记的东西。

### 不要做的事

- **不要给 `users` 加 `tenant_id`**。那会破坏「一个人一个账号」，
  而多工作室教师是这个市场的常态。
- **不要给平台表加策略**。超级管理员控制台读的就是跨租户视图，
  给它加策略等于要求它自己关掉策略，那还不如没有。

## 四、只做必须的检查：测试分层

现状：2564 条用例，其中连真库的 17 条，对钱这一层发请求的 0 条。

问题不是数量少，是**分布错了**。绝大多数用例在断言源码文本，而这一轮三个
上线 bug 一个都不是源码文本能看见的。

### 方案 3：三层，各司其职

| 层 | 回答什么 | 现在 | 建议 |
|---|---|---|---|
| **结构层**（静态） | 「两份清单没漂」「守卫没被绕过」 | 约 2500 条 | **不再增加**，只在抓到真 bug 后补 |
| **不变量层**（真库） | 「数据库自己拦得住」 | 17 条 | 加 RLS 那 3 条即可 |
| **行为层**（真请求 + 有数据的租户） | 「这条路由真的能用」 | 0 条 | 加**一条冒烟链**，不是 50 条 |

### 那条冒烟链，一条就够

不测 50 条路由。测**一个工作室一天里真的会走的一条链**：

```
建付款方 → 开草稿 → 加行 → 开具 → 登记收款 → 断言余额为 0
        → 老师签到 → 课酬清单出数
        → 学员请假 → 断言三个答案 + 补课额度
```

一条链穿过约 12 条路由和 6 张表。它捕获的是「整条路走不通」——
而这一轮三个 bug 里有两个正是这种。剩下 38 条路由的独立测试，
**在 RLS 到位之后收益极低**，因为最危险的那一类（跨租户）已经由构造保证了。

### 顺带砍掉的

昨天提的「每条路由的权限拒绝测试」也不必要：`auth.py` 的权限表已有静态断言，
`test_money_layer.py` 已有「每条路由必须声明 permission_required」的守卫。
两条加起来覆盖了「声明了」和「声明对了」，缺的只是「装饰器真的生效」——
那一条写**一次**就够，不用写 50 次。

## 五、工作流

### 方案 4：把 `verify_local.sh` 分成两个档

现在它是一个全量档，每次都跑完。实际使用中有两种场景：

| 档 | 何时用 | 内容 |
|---|---|---|
| **快** | 每次改动后 | pytest + CMS 编译 + 编译产物是否与源码同步 |
| **全** | 发版前 | 快档 + 隔离套件 + 冒烟链 + 静态页面打开 + 打包校验 |

现在的问题不是慢，是**「全量」让人倾向于少跑**。分档之后，快档可以每次都跑。

### 方案 5：一条写进 AGENTS.md 的规矩

> 改动**决定东西画在哪儿**的代码（定位方式、DOM 中的位置、grid/flex 结构、
> 断点）时，DOM 查询不算验证。必须至少做到其一：桌面与手机两个宽度截图并看；
> 或量 `getBoundingClientRect()` 断言相对关系。

这一轮我为此连发 v10.2.1、v10.2.2 两个补丁版本。零成本。

### 方案 6：发布前的一条真问题

`entrypoint.sh` 跑迁移用属主角色，应用用受限角色——这意味着**部署顺序有了
依赖**：迁移必须先跑完，应用才能起。现在是同一个容器同一个角色，没这个问题。

切换时要确认 entrypoint 的迁移步骤和应用启动步骤用的是不同连接串，
且迁移失败时应用不启动。这一条要在第一节实施时一起做，不能事后补。

## 六、稳定性：不属于隔离的三项

### 6.1 没有连接池

`connect()` 每请求开一条新连接。在工作室量级（几十并发）完全够用，
而且**对 RLS 有利**（没有池化连接串味的风险）。

**建议：暂时不动。** 如果将来要加池，必须同时确认 `SET LOCAL` 而不是 `SET`
（方案 2 已经写成 LOCAL），否则会话变量会跟着连接跑到下一个租户的请求里——
那是比现在严重得多的泄漏。**先有 RLS 再有池子，顺序不能反。**

### 6.2 备份演练是真的跑过的

`pwestudio_remote.sh drill` 存在且能把备份恢复到一次性数据库。
**建议：给它一个定期节奏**（比如每月一次），并把结果记进 HANDOFF。
备份没演练过等于没有备份，这条现在做对了一半——有工具，没习惯。

### 6.3 演示租户每晚重置仍未装定时器

生产已有 demo 密钥，重置脚本能跑（v10.1.1 手工跑过）。缺的只是定时器。
演示数据会被访客改乱，而它现在是销售现场的样板。

## 七、优先级与代价

按「防住的损失 ÷ 力气」：

| # | 事项 | 代价 | 防住什么 |
|---|---|---|---|
| 1 | **应用换成非超级用户角色** | 半天 | 注入 = 整库沦陷；且是 RLS 的前提 |
| 2 | **73 张表启用 RLS**（四步走） | 1–2 天 | 「第 174 条路由忘了写 WHERE」 |
| 3 | 3 条结构测试替代 50 条路由测试 | 2 小时 | 让上一条可验证 |
| 4 | AGENTS.md 布局验证规矩 | 10 分钟 | 这一轮两个补丁版本 |
| 5 | 一条端到端冒烟链 | 半天 | 「整条路走不通」 |
| 6 | `verify_local.sh` 分快/全两档 | 1 小时 | 让快档真的每次都跑 |
| 7 | 改掉账单空状态那句不成立的承诺 | 10 分钟 | 文案替不存在的功能背书 |
| 8 | 备份演练定期化 + 演示重置定时器 | 半天 | 备份没演练等于没有 |

**1 和 2 是一件事，不该拆开做。** 单独做 1，安全性已经实质提升；
只做 2 不做 1，等于什么都没做（超级用户绕过 RLS）。

昨天那份方案里的「300 行路由测试」——**撤回**。做完 1、2、3 之后它就是多余的。

## 附：这份方案和上一份的区别

上一份问的是「怎么把每条路都测到」。
这一份问的是「怎么让不必测的路，走不到坏地方」。

数据库是唯一一个**所有代码路径都必须经过**的地方。把规则放在那里，
就不用在 173 个入口各放一遍——也不用写 173 条测试去检查它们都放了。

这也是「只做必须的检查」和「只隔离必须的数据」是同一句话的原因：
**隔离放对了位置，检查就自然变少了。**
